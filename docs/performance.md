# 性能

## 1. 重要な注意

**本書の数値はすべて計測前の目標であり、実測値ではない。** [開発規約](../.github/instructions/fsharp-dotnet.instructions.md) は計測なしに「高速」と断定することを禁じている。各マイルストーンで実測し、本書の値を実測値に置き換えるか、達成不能と判明した時点で目標自体を改訂する。

## 2. 基準ハードウェア

目標値は次の構成を基準とする。異なる構成での計測は、構成を明記して別に記録する。

| 項目 | 基準 |
| --- | --- |
| CPU | 8 物理コア以上 |
| メモリ | 32 GiB |
| ストレージ | NVMe SSD |
| OS | macOS（arm64）および Windows（x64）の両方 |

## 3. ベンチマーク コーパス

コミット SHA で固定し、再現可能にする。

| 名前 | 内容 | 用途 |
| --- | --- | --- |
| `micro` | 数百ファイルの合成ツリー | CI の全実行 |
| `medium` | 数千ファイルの実 OSS リポジトリ | CI の全実行 |
| `cjk` | CJK のファイル名・識別子・内容・レガシー符号化を含む | CI の全実行 |
| `pathological` | 巨大単一ファイル、深い階層、長い行、深い入れ子 | CI の全実行 |
| `linux` | Linux カーネル | 定期実行 |
| `chromium` | Chromium | 定期実行 |

`linux` と `chromium` は取得と実行に時間がかかるため、プルリクエストごとではなく定期実行とする（[テスト](testing.md)）。

## 4. 目標値

### 4.1 インデックス生成

| コーパス | 完全生成（目標） | 増分（1 ファイル変更、目標） |
| --- | --- | --- |
| `medium` | ≤ 10 秒 | ≤ 500 ms |
| `linux` | ≤ 5 分 | ≤ 1 秒 |
| `chromium` | ≤ 30 分 | ≤ 2 秒 |

増分更新の目標には、プロセス起動時間を含む。AI エージェントは短命プロセスとして頻繁に呼び出すため、起動時間はこの用途で支配的になり得る。

### 4.2 照会

| 指標 | 目標 |
| --- | --- |
| プロセス起動から結果出力まで（`chromium`、warm） | p50 ≤ 50 ms、p95 ≤ 150 ms、p99 ≤ 300 ms |
| シンボル完全一致検索 | p95 ≤ 20 ms |
| 部分一致検索（CJK 含む） | p95 ≤ 100 ms |
| 2 ホップ近傍探索 | p95 ≤ 50 ms |
| 最短経路（深さ上限あり） | p95 ≤ 200 ms |

cold 状態（ページ キャッシュなし）は別に計測し、warm と区別して記録する。

### 4.3 リソース

| 指標 | 目標 |
| --- | --- |
| インデックス生成時のピーク RSS | 既定上限 4 GiB。入力規模に依存せず上限内 |
| 照会時のピーク RSS | ≤ 256 MiB（mmap のページ キャッシュを除く） |
| 生成物サイズ | `chromium` で実測して確定。ソース総量に対する比率で記録 |
| ファイル ハンドル | 同時オープン数に上限を設ける |
| 使用しない CPU | アイドル時のポーリングを行わない |

RSS 上限は「守れなければ設計が誤り」という意味の制約である。入力規模に比例して増えるのであれば、[アーキテクチャ](architecture.md) の spill / 外部ソート設計が機能していない。

## 5. 計測方法

- Release 構成、最適化有効、デバッガー非接続、warmup 実施
- 平均だけでなく分布（p50 / p95 / p99）、allocation、GC 回数、working set、成果物サイズを記録する
- 同一マシン・同一ランタイムで比較する。異なる実行間の比較には条件を明記する
- benchmark 専用依存は benchmark プロジェクトに隔離し、製品成果物に含めない
- cold / warm を区別する。cold 計測ではページ キャッシュを明示的に落とす

## 5.1 実測値

本節には実測した値だけを記録する。目標値（4）と混同しないこと。

### 内容ハッシュ（2026-09 時点）

| 条件 | 値 |
| --- | --- |
| 環境 | macOS / Apple Silicon、.NET 10、Release、`InProcessEmitToolchain` |
| 手法 | BenchmarkDotNet、warmup 3 回、計測 5 回 |
| 入力 | 251 バイト周期の合成データ |

| 入力サイズ | `SHA256`（BCL、採用） | `Blake3`（自前、不採用） | 比 |
| --- | --- | --- | --- |
| 4 KiB | 1.85 µs | 9.33 µs | 5.03 |
| 64 KiB | 27.0 µs | 150.8 µs | 5.58 |
| 1 MiB | 430 µs | 2,413 µs | 5.61 |
| 16 MiB | 6,884 µs | 38,654 µs | 5.62 |

いずれも割り当てはゼロである。BLAKE3 の実効 throughput は約 434 MB/s。

この結果を受けて、**本番経路のハッシュは BCL の `SHA256` へ切り替えた**（[設計判断](decisions.md) ADR-8）。
自前実装の採用条件は「代表 workload の benchmark で BCL 実装を上回ること」であり、scalar BLAKE3 はこれを満たさない。

- 配列添字による素朴な実装は baseline の約 19 倍遅かった。圧縮関数の状態とメッセージ語をローカル変数へ置き、7 ラウンドを完全展開して約 3.4 倍改善したが、なお 5 倍以上の差が残る
- 残る差は主にハードウェア支援の有無による。`SHA256` は Apple Silicon の暗号命令を使い、BLAKE3 は現状 scalar 実装である
- SIMD 化（`Vector128` / `Vector256`）は未着手。完成して baseline を上回った時点で採用を再評価する（M7）

### ハッシュ切り替えの全体影響（2026-09 時点）

primitive 単体ではなく `index` / `verify` 全体で測る。単体の 5 倍差がそのまま全体に出るわけではないため、
採用判断は全体 workload で行う。

| 条件 | 値 |
| --- | --- |
| 環境 | macOS / Apple Silicon、.NET 10、Release publish、warm cache |
| 入力 | 20,000 個の小ファイル（78 MB）+ 6 個の 20 MiB ファイル、計 197 MB |
| 手法 | 実行時間の中央値。`index` は毎回 `.srcnet` を削除してから計測 |

| 計測 | 変更前 (BLAKE3) | 変更後 (SHA-256) | 比 |
| --- | ---: | ---: | ---: |
| `index`（既定の並列度） | 3.78–4.01 s | 3.72–3.89 s | 約 1.0 |
| `index --jobs 1`（大容量ファイルのみ 119 MB） | 0.62–0.65 s | 0.28–0.45 s | 約 1.8 |
| `index --jobs 1`（小ファイル 20,000 個） | 3.92 s | 3.88 s | 約 1.0 |
| `verify`（セグメント再ハッシュ） | 0.171–0.197 s | 0.126–0.153 s | 約 1.3 |

- ハッシュが支配的な経路（大容量ファイル、`verify`）で明確に改善する
- 小ファイル主体の `index` はディレクトリ走査と 1 ファイルあたりの I/O が支配的で、ハッシュの差は表に出ない
- いずれの条件でも regression はない
- **未検証:** Windows での同条件比較は runner が無く未実施

本節へ追記する。macOS の大文字小文字を区別しないファイルシステムでは、Linux カーネルに実在する
大文字小文字だけが異なるファイルが取得段階で欠ける。厳密な件数比較には、区別するファイル
システム上での取得が要る。

### 照会の応答時間とピーク RSS（M4 初期実装、修正前）

`search` / `show` / `neighbors` / `context` を実測した。プロセス起動を含む「呼び出しから
結果出力まで」を測る。AI エージェントは短命プロセスとして頻繁に呼び出すため、起動時間は
この用途で支配的になる（4.1 の注記）。

| 条件 | 値 |
| --- | --- |
| 環境 | macOS 26.6 / Apple M1 Max（10 コア）/ 64 GiB / NVMe、.NET 10、Release publish、warm cache |
| 入力 | 合成コーパス 15,000 ファイル / 59 MiB。270,121 ノード / 255,000 シンボル、生成物 71 MiB |
| 手法 | 各コマンドを warmup 3 回のうえ 15 回実行。`--json` 出力を捨てて計測 |

| 計測 | p50 | p95 | ピーク RSS |
| --- | ---: | ---: | ---: |
| プロセス起動のみ（`--version`） | 65.3 ms | 70.1 ms | — |
| `search`（完全一致） | 191.4 ms | 196.0 ms | 143 MiB |
| `search`（部分一致、`--limit 20`） | 226.7 ms | 228.9 ms | 143 MiB |
| `show` | 86.6 ms | 88.3 ms | 53 MiB |
| `neighbors --depth 2` | 97.7 ms | 100.4 ms | 53 MiB |
| `context`（2 語） | 291.8 ms | 320.2 ms | 161 MiB |

**目標との差:**

| 指標 | 目標 | 実測 | 判定 |
| --- | --- | --- | --- |
| 起動から結果出力まで | p50 ≤ 50 ms | 86.6–291.8 ms | **未達** |
| シンボル完全一致検索 | p95 ≤ 20 ms | 196.0 ms | **未達** |
| 2 ホップ近傍探索 | p95 ≤ 50 ms | 100.4 ms | **未達**（起動を除けば約 32 ms で達成） |
| 照会時のピーク RSS | ≤ 256 MiB | 53–161 MiB | 達成 |

未達の原因は 2 つに分かれる。

1. **プロセス起動が 65 ms を占める。** どのコマンドもこのぶんを必ず払う。`neighbors` は
   起動を除けば約 32 ms で目標内に収まっている。ReadyToRun / Native AOT の比較（M7）で
   縮める余地がある。目標そのものが「起動を含む」と定義されている以上、配布形態を決めるまで
   この項目は達成できない
2. **検索索引がない。** M2 の成果物は名前の索引を持たないため、`search` は文字列表と
   ノード表を全走査する。上の条件で約 126 ms かかり、規模に比例して伸びる。全走査へ
   黙って退行させず、`usedIndex: false` と診断で明示している。索引は M5 で追加する

`context` が最も遅いのは、語ごとに検索を繰り返すためである。索引が入れば同じ比率で縮む。

### 028・029 の完成に向けた実コーパス検証（2026-09-07）

予算制御・有向探索・字句索引・HTML 出力を修正した後の測定である。初期実装の値とは
コーパスと配布形態が異なるため、比率だけで性能改善を一般化しない。

| コーパス | Edge/Chromium 系の実ソース、HEAD `4cc82d0685dd4a81da627dde207143ea570ad42f` |
| グラフ | T0、1,152,053 ノード / 1,152,052 エッジ / 1,048,444 ファイル |

元のソースと既存成果物は変更せず、検証用コピーへ索引を生成した。検索は索引を使用し、
表の照会はいずれも安全上限による探索打ち切りなしで完了した。

| 照会 | p50 ms | p95 ms | p99 ms | ピーク RSS MiB |
| --- | ---: | ---: | ---: | ---: |
| 起動のみ（`--version`） | 52.3 | 53.1 | 53.2 | 53.6 |

- 端から端の p95 ≤ 150 ms、p99 ≤ 300 ms、RSS ≤ 256 MiB は、この条件で目標内だった。
  RSS は mmap の常駐ページを含むため、除外後の上限に対しても保守的な判定になる
- **p50 ≤ 50 ms は未達。** 起動のみで約 52 ms を要する。検索処理だけでは完全一致を含む
  実クエリが中央値 9.21 ms、p95 9.38 ms、割り当て 7,512 バイトだったが、起動込みの目標を
  この値で代用しない
- 30 標本の nearest-rank p99 は観測最大値であり、本番の tail latency を統計的に保証しない
- Native AOT も試したが、FSharp.Core の printf / Lazy に由来する IL3050・IL2060・IL2091 などで
  厳格な publish が失敗した。警告を抑制して採用することはしなかった
- 通常 ReadyToRun は managed 配布より短命プロセスの応答を短縮した。workstation GC の差は小さく、
  composite/self-contained ReadyToRun は起動が約 62 ms と遅かったため、既定値へ採用しない
- Windows の同条件測定、cold cache、全入力の T2 生成は未実施。M7 の性能目標全体を達成した
  という判定ではない

HTML は実際の `content/browser` 周辺を深さ 3 で切り出した。生成は warmup 3 回 + 7 回、
ブラウザーはサイズごとに新しい隔離プロファイルで 5 回、オフラインで逐次測定した。

| ノード | Chrome の標本ピーク RSS 合計 MiB | Edge の標本ピーク RSS 合計 MiB |
| ---: | ---: | ---: |
| 500 | 1,329.8 | 1,740.3 |
| 2,000 | 1,341.5 | 1,750.9 |
| 5,000 | 1,361.7 | 1,767.3 |

ブラウザーの値は隔離したプロセス群の RSS を 100 ms 間隔で合計した最大値であり、
共有ページの二重計上とブラウザー本体・初期タブを含む。グラフだけのメモリではなく、
短い瞬間ピークは捕捉できない。外部ページ要求、ページ例外、観測上のフリーズはなかった。

### 構文解析器の構築と成果物サイズ（2026-09 時点）

構文解析器として tree-sitter を再利用する（[設計判断](decisions.md) ADR-3）。
同梱する言語数が成果物サイズに直結するため、実測を記録する。

| 条件 | 値 |
| --- | --- |
| 環境 | macOS / Apple Silicon、Apple clang 21 |
| 対象 | ランタイム 1 件 + 文法 11 件（c, cpp, python, rust, go, java, javascript, csharp, typescript, tsx, fsharp） |

| 指標 | 実測 |
| --- | --- |
| 構築時間（取得済み、`-O2`） | 11.0 秒 |
| 共有ライブラリのサイズ | 20.7 MiB |
| ランタイム単体のオブジェクト | 256 KiB |

サイズは同梱する文法の数にほぼ比例する。`parser.c` の大きい C++ と C# が支配的で、
この 2 つを外すと大幅に縮む。既定で同梱する言語の範囲は M8 で決める。

未計測の項目（`chromium` コーパス、増分更新、cold 状態の照会）は、
対応するコーパスと機能が揃った時点で追記する。

## 6. 最適化の対象領域

規模から、次が支配的になると想定する。実測で確認してから着手する。

| 領域 | 想定される手法 |
| --- | --- |
| ファイル走査 | ディレクトリ単位の並列化、`stat` 呼び出しの削減 |
| 内容ハッシュ | SIMD 実装、mmap との比較 |
| 字句・構文走査 | 分岐削減、SIMD による区切り探索、割り当て回避 |
| エッジ解決 | 外部マージ ソート、基数ソート、SIMD による集合演算 |
| 索引探索 | 分岐予測に優しい配置、ビットマップの SIMD 演算 |
| 中心性反復 | CSR 上の逐次走査、キャッシュ局所性 |
| 起動時間 | mmap による遅延読み込み、初期化の最小化、ReadyToRun / Native AOT の比較 |

いずれも「速そうだから」ではなく、profiler で hot path を特定し、baseline との benchmark 比較で優位性を確認してから採用する。

## 7. 回帰防止

- 性能に影響する変更では、変更前 baseline との比較結果を必ず記録する
- 性能または資源使用の回帰がある変更は完了扱いにしない
- 定期実行の大規模ベンチマークで、時系列の推移を追跡する
