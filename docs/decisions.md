# 設計判断の記録

主要な決定と、その根拠・却下した代替案を記録する。決定を覆す場合は、該当項目を「改訂」として更新し、履歴を残す。

---

## ADR-1: グラフ生成の全工程で AI を使わない

**状態:** 確定

**文脈:** 本プロジェクトの目的は AI の利用コスト削減である。既存ツールはコードの構文解析には LLM を使わないが、コミュニティ命名、ドキュメント抽出、要約などで LLM を使う。

**決定:** 生成・照会のすべての経路で、モデル推論・埋め込み生成・外部 API 呼び出しを行わない。

**帰結:**

- グラフ構築コストがゼロになり、大規模リポジトリでも繰り返し実行できる
- 完全にオフラインで動作し、ソースが外部へ出ない
- 決定性が得られ、検証とキャッシュが可能になる
- **代償:** 意味的な要約と自然言語理解ができない。`explain` は事実の列挙に留まり、コミュニティ名は機械的なラベルになる。検索は字句一致に限られる

**却下した代替案:**

- *ローカル小規模モデルの同梱*: モデル配布が必要になり、成果物サイズ・起動時間・決定性・移植性のすべてを損なう。「軽量」要件と両立しない
- *埋め込みのみ使用*: モデル実行が必要な点は同じ。加えて数千万行規模での埋め込み生成コストが目的に反する

## ADR-2: 列指向 + memory-mapped セグメントを採用する

**状態:** 確定（実装時に実測で検証する）

**文脈:** 規模目標は 10^7 〜 10^8 ノード、10^8 〜 10^9 エッジ。参照実装は単一 JSON または SQLite を使うが、graphify は `graph.json` に上限を設けている事実が示すとおり、この形式は規模上限に直面する。

**決定:** 固定長レコードの列指向表、重複排除した文字列 blob、エッジ種別ごとの CSR 隣接表を、不変セグメントとして memory-mapped で読む。

**帰結:**

- 起動時に全体を読まないため、起動時間が生成物サイズにほぼ依存しない
- 逆引き（呼び出し元の探索）が定数時間の範囲アクセスになる
- SIMD による集合演算と走査が可能になる
- **代償:** 自作形式のため、版管理・検証・移行を自前で持つ必要がある。汎用ツールで直接開けない

**却下した代替案:**

- *単一 JSON*: 逐次解析コストと常駐メモリが規模に比例する。規模目標で成立しない
- *SQLite*: 行あたりのオーバーヘッドと結合コストが支配的になる。CSR 相当の隣接走査性能が出ない
- *組み込みグラフ DB*: 依存が重く、「軽量」要件と製品依存の原則に反する

## ADR-3: 構文解析器の選定は実測で決める

**状態:** 未決（P0 言語の実装時に決定する）

**文脈:** 多言語の構文解析には既存の文法資産（tree-sitter 等）を使う選択肢と、対象を絞った専用走査器を自作する選択肢がある。[開発規約](../.github/instructions/fsharp-dotnet.instructions.md) は、外部ライブラリ採用前に目的特化の自前実装を比較することを求めている。

**評価軸:**

| 軸 | 内容 |
| --- | --- |
| 速度 | C/C++ の大規模コーパスに対する throughput と p95 |
| メモリ | ファイルあたりのピーク使用量と割り当て |
| 移植性 | macOS / Windows での動作と配布方法 |
| 決定性 | 同一入力での結果一致 |
| 安全性 | ネイティブ コードのメモリ安全性、fuzz 耐性 |
| 保守性 | 対応言語を増やす際のコスト |
| 依存 | 製品成果物のサイズと攻撃面 |

**制約（選択によらず必須）:** 対象リポジトリから文法やプラグインを動的に読み込まない（[セキュリティ](security.md) C-1）。

**判断時期:** マイルストーン M2。

## ADR-4: F# 10 / .NET 10 を採用する

**状態:** 確定

**文脈:** 参照実装はいずれも Python であり、数千万行規模で必要な throughput とメモリ制御を得られない。

**決定:** F# 10 / .NET 10 を使う。

**根拠:**

- `Span`、`ArrayPool`、`stackalloc`、SIMD 組み込み、memory mapping など、必要な低レベル制御が揃っている
- 判別共用体とパターン マッチングが、ノード種別・エッジ種別・確度の表現に適する
- 単一ランタイムで macOS と Windows を対等に扱える
- **代償:** 既存の構文解析文法資産の多くが C / Rust / Python 前提であり、相互運用または自作が必要になる（ADR-3）

## ADR-5: 精度の限界を隠さない

**状態:** 確定

**文脈:** AI を使わない静的解析では、仮想呼び出し・関数ポインタ・マクロ生成コードの解決先を一意に決められない。

**決定:** 解決できないものを推測で確定させず、`AMBIGUOUS` として候補と根拠段階を保持する。

**帰結:** 出力の信頼性が担保され、利用側の AI が誤った前提で推論することを防ぐ。反面、単一の答えを期待する用途では冗長になる。

## ADR-6: 全文検索を v1 の対象外とする

**状態:** 確定（範囲の決定）

**文脈:** 数千万行の全文索引は、シンボル索引とは規模も設計も異なる問題である。

**決定:** v1 の索引対象は識別子・シンボル名・パスに限定する。ソース本文の全文検索は範囲外とし、必要になった時点で別途設計する。

**根拠:** 目的は「AI が読むべき箇所を絞る」ことであり、全文検索は既存の grep 系ツールが担える。限られた実装資源を、既存ツールで代替できない構造解析へ振り向ける。

## ADR-7: ソースの改行を LF、符号化を BOM なし UTF-8 に固定する

**状態:** 確定（M0 で決着）

**文脈:** 当初の `.editorconfig` は全ファイルに CRLF と UTF-8 BOM を指定していた。BOM は一部のツールで問題を起こし、CRLF は macOS 側の開発と衝突する。加えて、作業ツリーの改行が OS で変わると、同じリポジトリを macOS と Windows で解析したときに内容ハッシュが変わり、決定性要件 NFR-11 が破れる。

**決定:** リポジトリ内の全テキスト ファイルを BOM なし UTF-8 と LF に統一する。`.gitattributes` の `* text=auto eol=lf` で作業ツリーの改行を固定し、`.editorconfig` を同じ方針に合わせる。Windows でのみ実行される `.cmd` / `.bat` / `.ps1` だけは CRLF を維持する。

**帰結:**

- 成果物の改行はプラットフォームによらず固定される。srcnet 自身の出力も LF に固定する
- 自リポジトリを srcnet で解析したときの内容ハッシュが OS に依存しない
- **代償:** Windows のメモ帳など、LF のみのファイルを扱いにくいツールがある

**却下した代替案:**

- *CRLF + BOM の維持*: 改行が OS 差の原因になり、決定性の検証を CI で行う際に不要な差分を生む
- *`.gitattributes` を置かずに `.editorconfig` だけで統一*: エディタ設定は git のチェックアウト時の変換を制御できず、Windows の `core.autocrlf=true` で作業ツリーが CRLF になる

## ADR-8: 内容ハッシュに BLAKE3 の自前実装を用いる

**状態:** 確定（実測で採用条件を検証済み。SIMD 化は未着手）

**文脈:** 製品コードへの NuGet 追加は原則禁止であり、[開発規約](../.github/instructions/fsharp-dotnet.instructions.md) は自前実装を最優先候補として比較することを求める一方、優位性が確認できない自前実装は採用しないとしている。内容ハッシュはリポジトリの全バイトが通る hot path で、インデックス生成の所要時間を支配し得る。

**決定:** BLAKE3 を自前で実装し、内容ハッシュ、ノード ID の導出、セグメントのチェックサムに用いる。これは暗号用途ではなく変更検出と完全性検査の用途であり、[セキュリティ](security.md) 5 の「暗号プリミティブを自作しない」制限とは区別される。正しさは公式テスト ベクターとの一致で担保する。

**実測（Apple Silicon / .NET 10 / Release）:** 素朴な配列添字の実装は BCL の `SHA256`（ハードウェア アクセラレーション有効）より約 19 倍遅く、採用条件を満たさなかった。圧縮関数の状態とメッセージ語をローカル変数に置き、7 ラウンドを完全展開して境界検査と再読み込みを除いたところ大幅に改善した。最新の数値は [性能](performance.md) に記録する。

**帰結:**

- 製品成果物の依存閉包は `FSharp.Core` と自リポジトリのアセンブリのみで、CI で機械的に検証される
- 圧縮関数は通常の F# idiom から意図が読み取りにくい形になっている。保守時に配列添字の実装へ戻してはならない
- **未了:** `Vector128` / `Vector256` による SIMD 化は未着手で、ハードウェア支援のある SHA-256 には及ばない。規模検証（M7）で hot path として再評価する

**却下した代替案:**

- *`SHA256` で代用する*: BCL のハードウェア アクセラレーションは速いが、[グラフ モデル](graph-model.md) 4.2 の ID 定義と [ストレージ](storage.md) 6.1 の変更検出が BLAKE3 を前提にしており、木構造ハッシュによる将来の並列化余地も失う
- *BLAKE3 の NuGet パッケージ*: 製品コードへの依存追加にあたり、ネイティブ ライブラリを伴うものは攻撃面と配布形態の制約も増やす

| 項目 | 内容 |

| Linux の位置づけ | 解析対象としての Linux カーネルは主目標だが、実行環境としての Linux を対応プラットフォームに含めるかは未決 |

| レガシー符号化の復号 | M1 では符号化の判定までを行い、復号は未実装。`System.Text.Encoding.CodePages` は製品依存の追加になるため、抽出（M2）の要件と併せて決める |
