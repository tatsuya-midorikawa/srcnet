# 設計判断の記録

主要な決定と、その根拠・却下した代替案を記録する。決定を覆す場合は、該当項目を「改訂」として更新し、履歴を残す。

---

## ADR-1: グラフ生成の全工程で AI を使わない

**状態:** 確定

**文脈:** 本プロジェクトの目的は AI の利用コスト削減である。既存ツールはコードの構文解析には LLM を使わないが、コミュニティ命名、ドキュメント抽出、要約などで LLM を使う。

**決定:** 生成・照会のすべての経路で、モデル推論・埋め込み生成・外部 API 呼び出しを行わない。

**帰結:**

- グラフ構築の LLM 利用料はゼロになる。CPU・I/O・保存領域の費用は残り、規模検証が必要である
- 完全にオフラインで動作し、ソースが外部へ出ない
- 決定性が得られ、検証とキャッシュが可能になる
- **代償:** 意味的な要約と自然言語理解ができない。`explain` は事実の列挙に留まり、コミュニティ名は機械的なラベルになる。検索は字句一致に限られる

**却下した代替案:**

- *ローカル小規模モデルの同梱*: モデル配布が必要になり、成果物サイズ・起動時間・決定性・移植性のすべてを損なう。「軽量」要件と両立しない
- *埋め込みのみ使用*: モデル実行が必要な点は同じ。加えて数千万行規模での埋め込み生成コストが目的に反する

## ADR-2: 列指向 + memory-mapped セグメントを採用する

**状態:** 不変セグメントと CSR は採用。完全な列分割の採否は実測で判断する

**文脈:** 規模目標は 10^7 〜 10^8 ノード、10^8 〜 10^9 エッジ。
全件の復号・常駐を照会ごとに行わず、近傍を連続した範囲として読める配置が必要である。

**決定:** 固定長レコード、重複排除した文字列 blob、エッジ種別ごとの CSR 隣接表を、
不変セグメントとして memory-mapped で読む。現行の `.nodes` / `.files` は 64 バイトの
レコード配列であり、すべての属性を独立した列に分割しているわけではない。

**帰結:**

- 起動時に全体を読まないため、起動時間が生成物サイズにほぼ依存しない
- 逆引き（呼び出し元の探索）が定数時間の範囲アクセスになる
- SIMD による集合演算と走査が可能になる
- **代償:** 自作形式のため、版管理・検証・移行を自前で持つ必要がある。汎用ツールで直接開けない

**却下した代替案:**

- *単一 JSON*: 逐次解析コストと常駐メモリが規模に比例する。規模目標で成立しない
- *SQLite*: 採用せず専用形式を先に実装した。優劣の一般化には同一 workload の比較が必要であり、性能上限を断定しない
- *組み込みグラフ DB*: 依存が重く、「軽量」要件と製品依存の原則に反する

## ADR-3: 構文解析器は tree-sitter を再利用する

**状態:** 確定

**文脈:** 対応予定の言語は C / C++ に始まり、Rust、Python、JavaScript / TypeScript、Java、Go、C#、Objective-C まで広がる（[ロードマップ](roadmap.md) M2、M8）。[開発規約](../.github/instructions/fsharp-dotnet.instructions.md) は外部ライブラリの採用前に目的特化の自前実装を比較することを求めるが、その比較軸には「保守性: 対応言語を増やす際のコスト」も含まれる。

多言語対応が要件である以上、この軸が支配的になる。言語ごとに構文解析器を自作すると、言語数に比例して実装と追随の負担が増え、各言語の仕様変更に継続的に追従し続ける必要がある。速度で自前実装が上回る可能性があっても、10 以上の言語について正しさを保ち続ける費用は現実的でない。

**決定:** 構文解析には **tree-sitter** を再利用する。ランタイムと文法はいずれも MIT ライセンスで、`native/sources.json` に取得元・版・SHA-256 を固定する。

**根拠:**

| 軸 | 評価 |
| --- | --- |
| 保守性 | 文法は上流が保守する。言語追加には固定情報・相互運用の対応・抽出規則・ゴールデンが必要 |
| 速度 | インクリメンタル解析を前提とした C 実装で、大規模コーパス向けに設計されている |
| 誤り耐性 | 構文誤りを含むファイルでも部分的な木を返す。壊れたファイルが正常系である超大規模リポジトリの前提に合う |
| 決定性 | 同一入力・同一文法版から同一の木を返す |
| 移植性 | C11 のみに依存し、macOS / Windows のいずれでも構築できる |
| 依存 | ランタイムは約 250 KiB。文法は同梱する言語数に比例する |

**帰結:**

- 文法実装の保守は上流へ委ねる。構文木からグラフへの抽出規則は言語ごとに実装する
- 構文木の取得までを外部に委ね、srcnet は「木からグラフを作る」ことに実装資源を集中できる
- **代償 1:** 製品成果物にネイティブ コードが入り、メモリ安全性の検証責任が生じる。相互運用の境界では寿命・範囲・null を必ず検証し、fuzz テストの対象とする（[セキュリティ](security.md) 4）
- **代償 2:** 生成済みの文法 `parser.c` は 1 言語で数 MB から 30 MB あり、リポジトリへ同梱できない。版とチェックサムを固定したうえで構築時に取得する
- **代償 3:** 構築に C コンパイラが必要になる。構文解析器が無い環境では構造グラフと T1 の行指向抽出を継続する

**同梱する文法（実測で確認済み）:** C, C++, Python, Rust, Go, Java, JavaScript, C#, TypeScript, TSX, F#。

1 つのリポジトリが複数の文法を持つ場合があるため、`native/sources.json` は `subdirectory` で位置を指定できる。TypeScript（`typescript` と `tsx`）と F#（ionide/tree-sitter-fsharp）がこれに当たる。

- `.tsx` は JSX を含み TypeScript 文法では解析できないため、専用の `tsx` 文法を使う。言語としても `Tsx` を分けて記録する
- `.fsi` は本体と同じ `fsharp` 文法で解析する。ionide の `fsharp_signature` 文法は `module` 宣言を含む現実的なシグネチャ ファイルを解析できず、通常の文法が同じ入力を誤りなく解析したため採用しない。言語としては `FSharpSignature` を分けて記録する（C/C++ のヘッダーと同じ扱い）
- F# の文法は ABI 15 を要求するため、ランタイムは ABI 13〜15 に対応する v0.25.10 を用いる。v0.26 以降は `ts_parser_set_timeout_micros` と `ts_parser_set_cancellation_flag` を削除しているため、更新時は進捗コールバック API への移行が必要になる

**この決定が変えない制約:** 文法の一覧は**コンパイル時に固定**する。解析対象リポジトリの内容や設定から文法・プラグインを動的に読み込む経路は作らない（[セキュリティ](security.md) C-1）。tree-sitter は文法を共有ライブラリとして読み込む使い方もできるが、その経路は採らない。

**却下した代替案:**

- *言語ごとの専用走査器を自作する*: 速度では上回り得るが、対応言語数に比例して保守費用が増え、多言語対応という要件そのものと衝突する。段階的抽出の T1（行指向）は引き続き自前で行い、T2 以降を tree-sitter に委ねる
- *ANTLR + grammars-v4*: managed で完結する利点はあるが、生成される解析器が数千万行規模の throughput 目標に届かず、文法の品質も言語ごとにばらつく
- *各言語の公式コンパイラ フロントエンド*: 精度は最も高いが、言語ごとに別のランタイムと配布形態が必要になり、「軽量」「オフライン完結」と両立しない
- *tree-sitter の NuGet パッケージ*: 版の固定とチェックサム検証を自分で持てず、同梱する文法も選べない

## ADR-4: F# 10 / .NET 10 を採用する

**状態:** 確定

**文脈:** 参照実装はいずれも Python であり、数千万行規模で必要な throughput とメモリ制御を得られない。

**決定:** F# 10 / .NET 10 を使う。

**根拠:**

- `Span`、`ArrayPool`、`stackalloc`、SIMD 組み込み、memory mapping など、必要な低レベル制御が揃っている
- 判別共用体とパターン マッチングが、ノード種別・エッジ種別・確度の表現に適する
- 単一ランタイムで macOS と Windows を対等に扱える
- **代償:** 既存の構文解析文法資産の多くが C / Rust / Python 前提であり、相互運用または自作が必要になる（ADR-3）

---

## ADR-5: 精度の限界を隠さない

**状態:** 確定

**文脈:** AI を使わない静的解析では、仮想呼び出し・関数ポインタ・マクロ生成コードの解決先を一意に決められない。

**決定:** 解決できないものを推測で確定させず、`AMBIGUOUS` として候補と根拠段階を保持する。

**帰結:** 出力の信頼性が担保され、利用側の AI が誤った前提で推論することを防ぐ。反面、単一の答えを期待する用途では冗長になる。

## ADR-6: 全文検索を v1 の対象外とする

**状態:** 確定（範囲の決定）

**文脈:** 数千万行の全文索引は、シンボル索引とは規模も設計も異なる問題である。

**決定:** v1 の索引対象は識別子・シンボル名・パスに限定する。ソース本文の全文検索は範囲外とし、必要になった時点で別途設計する。

**根拠:** 目的は「AI が読むべき箇所を絞る」ことであり、全文検索は既存の grep 系ツールが担える。限られた実装資源を、既存ツールで代替できない構造解析へ振り向ける。

## ADR-7: ソースの改行を LF、符号化を BOM なし UTF-8 に固定する

**状態:** 確定（M0 で決着）

**文脈:** 当初の `.editorconfig` は全ファイルに CRLF と UTF-8 BOM を指定していた。BOM は一部のツールで問題を起こし、CRLF は macOS 側の開発と衝突する。加えて、作業ツリーの改行が OS で変わると、同じリポジトリを macOS と Windows で解析したときに内容ハッシュが変わり、決定性要件 NFR-11 が破れる。

**決定:** リポジトリ内の全テキスト ファイルを BOM なし UTF-8 と LF に統一する。`.gitattributes` の `* text=auto eol=lf` で作業ツリーの改行を固定し、`.editorconfig` を同じ方針に合わせる。Windows でのみ実行される `.cmd` / `.bat` / `.ps1` だけは CRLF を維持する。

**帰結:**

- 成果物の改行はプラットフォームによらず固定される。srcnet 自身の出力も LF に固定する
- 自リポジトリを srcnet で解析したときの内容ハッシュが OS に依存しない
- **代償:** Windows のメモ帳など、LF のみのファイルを扱いにくいツールがある

**却下した代替案:**

- *CRLF + BOM の維持*: 改行が OS 差の原因になり、決定性の検証を CI で行う際に不要な差分を生む
- *`.gitattributes` を置かずに `.editorconfig` だけで統一*: エディタ設定は git のチェックアウト時の変換を制御できず、Windows の `core.autocrlf=true` で作業ツリーが CRLF になる

---

## ADR-8: 内容ハッシュは BCL の SHA-256 を用い、自前 BLAKE3 は採用条件を満たすまで使わない

**状態:** 確定（2 度目の判断。自前 BLAKE3 は採用条件を満たさなかったため取り下げ）

**文脈:** 製品コードへの NuGet 追加は原則禁止であり、[開発規約](../.github/instructions/fsharp-dotnet.instructions.md) は自前実装を最優先候補として比較することを求める一方、**代表 workload の benchmark で BCL 実装を上回ることを自前実装の採用条件**としている。内容ハッシュはリポジトリの全バイトが通る hot path で、インデックス生成と検証の所要時間を支配し得る。

当初は BLAKE3 を自前実装して採用したが、同一条件の実測では BCL の `SHA256` に一貫して 5 倍以上遅く、採用条件と実測が矛盾していた。

**決定:** 内容ハッシュ、ノード ID の導出、セグメントのチェックサムに BCL の `SHA256`（`System.Security.Cryptography`）を用いる。用途は変更検出と完全性検査であり、[セキュリティ](security.md) 5 の趣旨（検証済みの platform API を使う）にも合致する。

自前 BLAKE3 の実装（`Srcnet.Core.Blake3`）は、SIMD 化して baseline を上回った時点で再評価するための参照実装として残す。**本番経路からは参照しない。** 公式テスト ベクターとの一致は引き続きテストで担保する。

**実測（macOS 15 / Apple Silicon / .NET 10 / Release / InProcessEmitToolchain）:**

| 入力 | SHA256 | 自前 BLAKE3 | 比 |
| --- | ---: | ---: | ---: |
| 4 KiB | 1.88 µs | 9.47 µs | 5.05x |
| 64 KiB | 27.6 µs | 156.0 µs | 5.66x |
| 1 MiB | 436 µs | 2,455 µs | 5.62x |
| 16 MiB | 6,990 µs | 39,260 µs | 5.62x |

全体 workload（20,000 個の小ファイル + 6 個の 20 MiB ファイル、計 197 MB、warm cache、中央値）:

| 計測 | 変更前 (BLAKE3) | 変更後 (SHA-256) |
| --- | ---: | ---: |
| `index`（既定の並列度） | 3.78–4.01 s | 3.72–3.89 s |
| `index --jobs 1`（大容量ファイルのみ 119 MB） | 0.62–0.65 s | 0.28–0.45 s |
| `index --jobs 1`（小ファイル 20,000 個） | 3.92 s | 3.88 s |
| `verify`（セグメント再ハッシュ） | 0.171–0.197 s | 0.126–0.153 s |

ハッシュが支配的な経路で約 1.8 倍速く、小ファイル主体の経路は同等で、regression はない。

**互換性と移行:** ハッシュを変えるとノード ID と成果物の内容が変わる。単純な置換ではなく版で明示する。

- `Ids.SchemeVersion` を 1 → 2
- `Format.FormatVersion` を 1 → 2
- `Manifest.ManifestVersion` を 1 → 2
- マニフェストのチェックサム項目名を `blake3` → `sha256`

旧版の成果物は読まずに `UnsupportedManifestVersion` / `UnsupportedFormatVersion` で拒否し、再生成を促す。増分更新（M5）以前であり、再生成の費用は 1 回のフル索引で足りる。

**帰結:**

- 製品成果物の依存閉包は `FSharp.Core` と自リポジトリのアセンブリのみで変わらない
- ハードウェア支援のある SHA-256 を使うため、対象 CPU の暗号命令の有無が性能に直結する
- 木構造ハッシュによる将来の並列ハッシュ余地は当面失う。必要になった時点で SIMD BLAKE3 と併せて再評価する
- **未検証:** Windows での同条件比較は runner が無く未実施。CI で計測できるようになった時点で本 ADR の数値を補う

**却下した代替案:**

- *scalar BLAKE3 のまま使い続ける*: 実測が採用条件を満たさず、全バイトが通る経路で 5 倍の CPU 時間を払う
- *SIMD BLAKE3 を先に完成させる*: 4-way / 8-way の並列圧縮は相応の規模で、正しさの検証も含めて M7 の作業になる。それまで採用条件を満たさない実装を本番経路に置かない
- *BLAKE3 の NuGet パッケージ*: 製品コードへの依存追加にあたり、ネイティブ ライブラリを伴うものは攻撃面と配布形態の制約も増やす

## ADR-9: レガシー符号化は変換表を同梱して自前で復号する

**状態:** 確定

**文脈:** M1 は符号化の**判定**までを行い、復号は M2 の要件と併せて決めることになっていた。
T2 は UTF-8 のバイト列を要求するため、Shift_JIS や EUC-JP のファイルを復号しなければ、
これらのファイルは T1 でも T2 でも識別子を正しく取り出せず、[テスト](testing.md) T-4 の
「文字化けと欠落がない」を満たせない。

**決定:** 必要な符号化（Shift_JIS / EUC-JP / ISO-2022-JP / GB18030 / Big5 / EUC-KR）だけを、
同梱した変換表で自前で復号する。UTF-16LE / BE は BCL の変換を使う。

変換表は `tools/generate_encoding_tables.py` が Python 標準ライブラリの CJK codec から生成し、
Deflate で圧縮した埋め込み資源としてリポジトリへコミットする。生成物を持つことで、
ビルドにも実行にも外部データの取得が要らない。

**根拠:**

| 軸 | 評価 |
| --- | --- |
| 依存 | 製品成果物の依存閉包は `FSharp.Core` と自リポジトリのアセンブリのみで変わらない |
| 成果物サイズ | 圧縮後で合計 137 KiB。展開は実際にその符号化へ出会ったときだけ行う |
| 正しさ | 表の出典は Python の CJK codec で、生成は決定的である。固定コーパスで往復を検証する |
| 供給網 | 実行時に外部ファイルを読む経路を作らない（[セキュリティ](security.md) C-1） |

**曖昧な判定の扱い:** 判定が単一の符号化へ確定しない場合、候補の先頭を確定値として扱わない
（ADR-5、完了済み 010）。EUC-JP のバイト列は Shift_JIS としても構造上妥当になるなど、
これらの符号化は原理的に構造だけでは区別できない。したがって既定では復号せず、候補を
成果物へ残して抽出を行わない。利用者は `srcnet index --assume-encoding <名>` で符号化を
明示でき、その指定が候補に含まれる場合だけ適用する。指定は利用者が持ち込んだ事実であって、
srcnet の推測ではない。適用した符号化は `manifest.json` へ記録する。

**帰結:**

- 一意に判定できるファイル（UTF-8、UTF-16、ISO-2022-JP など）は既定で欠落なく抽出される
- 曖昧なファイルは、誤った復号による文字化けを成果物へ載せる代わりに、抽出を見送る
- EUC-JP の 3 バイト列（JIS X 0212 の補助漢字）は表に持たず、置換文字にして継続する。
  ソース コードでの使用が実質的に無いためであり、必要になった時点で表を足せばよい
- **代償:** 変換表の保守責任を負う。上流の codec が変わった場合は再生成と差分の確認が要る

**却下した代替案:**

- *`System.Text.Encoding.CodePages` を製品依存に追加する*: 実装費用は最小だが、製品コードへの
  NuGet 追加は原則禁止であり、依存閉包の検査（[テスト](testing.md) T-3）の前提も変わる。
  表 137 KiB を自前で持つほうが、依存を増やすより制御しやすい
- *非 UTF-8 を T1 のみに縮退させる*: 実装は最小だが、T1 も識別子の切り出しに復号を要するため、
  CJK 圏のリポジトリで識別子が壊れる。T-4 を満たせない
- *統計的な符号化推定で曖昧さを解消する*: 実行ごとに結果が揺れ得るうえ、推測を確定として
  出力しないという不変条件（[グラフ モデル](graph-model.md) 3）に反する

---

## ADR-10: Linux を対応実行環境に含めない

**状態:** 確定

**文脈:** 解析**対象**としての Linux カーネルは主目標だが、実行**環境**としての Linux を対応
プラットフォームに含めるかは M2 で決着させることになっていた。[テスト](testing.md) 4 は
「Linux ランナーはコーパス取得の効率のために使ってよいが、合否判定には使わない」という
暫定の位置づけのままだった。

M2 の実測（[性能](performance.md) 5.1）で、`linux` コーパスの走査と抽出が macOS で 72 秒、
生成物 1.66 GiB という規模が分かった。取得と実行の費用は無視できない。

**決定:** Linux を**対応実行環境に含めない**。Linux ランナーの用途は、大規模コーパスの
取得と補助的な検証に限る。合否判定は macOS と Windows で行う。

**根拠:**

| 軸 | 評価 |
| --- | --- |
| 決定性の検証費用 | 対応環境を 3 つにすると、[テスト](testing.md) T-1 の 3 が 2 通りから 3 通りの突き合わせになる。組み合わせは環境数の 2 乗で増える |
| ファイルシステムの差異 | 大文字小文字の区別、パス長、リンクの扱いが 3 通りになる。macOS（既定で区別しない）と Linux（区別する）の差は、すでに Windows で扱っている差と重なる部分が多いが、同一ではない |
| ネイティブ構築 | tree-sitter の構築対象が 1 つ増える。文法は同じでも、共有ライブラリの形式と配布形態が増える |
| 利用者 | 想定する利用者は AI エージェントを動かす開発端末であり、macOS と Windows が支配的である |
| 取得効率 | Linux ランナーは最も安価で速い。ただしこの利点は「コーパスの取得」に限れば、合否判定に使わなくても得られる |

**帰結:**

- 対応環境は macOS と Windows の 2 つに固定される。決定性の突き合わせは 1 対で済む
- Linux 上で動作しないことを意図するものではない。.NET 10 の移植性により動作は見込めるが、
  検証していない以上「対応」とは呼ばない
- 大規模コーパスの取得には Linux ランナーを使ってよい。ただし取得したコーパスに対する
  索引と検証は macOS / Windows のランナーで行う
- **代償:** 大規模コーパスの定期実行が、より高価なランナーに縛られる。実行基盤の制約は
  [ロードマップ](roadmap.md) の未決事項として引き続き扱う

**却下した代替案:**

- *Linux を対応環境に含める*: 合否判定の対象を 3 つにすると、決定性の突き合わせと
  ファイルシステム差異の検証が増える。M2 時点でその費用に見合う需要が確認できていない
- *Linux を「動作するが未サポート」として明記する*: 未検証の環境について何かを保証する
  ことになる。検証しないなら何も言わないほうが正確である

実装前に決着させるべき事項を、[ロードマップ](roadmap.md) の未決事項と併せて管理する。

| 項目 | 内容 |
| --- | --- |
| 同梱する文法の範囲 | 同梱言語を増やすほど成果物が大きくなる。既定で同梱する言語と、利用者が選べるようにするかを M8 で決める |
| 生成物の配布 | Native AOT / 単一ファイル / フレームワーク依存のいずれで配布するか。起動時間・成果物サイズ・グローバリゼーション データの実測で決める |
| 複数リポジトリの統合単位 | 統合グラフを単一生成物とするか、リポジトリごとの生成物を照会時に結合するか |
| セグメントの分割ビュー読み取り | 現在の mmap 読み取りは単一ビューで扱える 2 GiB までを上限とし、超える場合は明示的に失敗する。Chromium 規模で必要になる分割ビューは M4 で設計する |
