# ロードマップ

各マイルストーンは、[要件](requirements.md) 6 の受け入れ基準を満たしたときに完了とする。特に「macOS と Windows の両方で検証済み」と「性能回帰なし」は全マイルストーン共通の完了条件である。

## 次の優先順位

| 優先度 | 作業 | 完了の根拠 |
| --- | --- | --- |
| P0 | 現行実装の整合性と CI 安定化 | 破損データ・同時公開・CJK の回帰項目、両 OS の実行、同一入力の成果物一致 |
| P1 | 大規模コーパスの取得条件と測定の再現性 | 正しい固定 SHA、欠損のない作業ツリー、macOS / Windows の測定記録（backlog 026） |
| P1 | メモリ有界化と性能非劣化の仕上げ | 退避・外部ソート・128 MiB 分割・予算制御を実装。代表 / 上限コーパスの RSS と時間の受け入れは未達（037） |
| P2 | M3 の参照解決 | 参照候補を推測せず解決し、確度・解決率・曖昧さの内訳を記録する |
| P2 | M4 の n-gram 転置索引と起動時間 | 現行 lookup を baseline とし、両 OS の cold / warm・CJK・tail latency を比較する |
| P3 | M5 以降 | 増分等価性を先に確立し、解析・言語拡大・公開準備へ進む |

以降の状態は実装の有無を表す。CI の設定が存在することを、実行済み・完了の証拠にしない。

## M0 — 基盤

状態: 実装済み。両 OS の CI 安定化は継続中。

- ソリューションとプロジェクト構成の作成（`Text` / `Core` / `Discovery` / `Storage` / `Cli` と対応するテスト）
- CI の構築（macOS + Windows マトリクス、ビルド・テスト・決定性・依存閉包の検査）
- ベンチマーク プロジェクトの雛形と、内容ハッシュの baseline 比較
- `.editorconfig` の改行・BOM 方針の確定（[設計判断](decisions.md) ADR-7）

**完了条件:** 両 OS の CI が緑。空の CLI が両 OS で起動する。

## M1 — 構造グラフ

状態: 構造グラフは実装済み。大規模コーパスの両 OS 受け入れは未完了。

- ファイル走査、無視設定、リンクと循環の処理
- 言語判定、エンコーディング検出、内容ハッシュ
- `Repository` / `Directory` / `File` ノードと `CONTAINS` エッジ
- 論理パス正規化（NFC、区切り統一）と ID 計算

**完了条件:** `linux` コーパスの走査が完了し、両 OS で成果物がバイト一致する。

**未了:**

- `linux` の macOS 測定記録はあるが、当時の SHA 記録に誤りが見つかり再測定が必要。
  Windows 側も未了（[性能](performance.md) 5.1、backlog 026）
- `--memory-limit`、spill、外部ソートの受け入れ。残る大域表と走査キューの保持を解消し、両 OS の実測で確認する
- 走査項目数が上限に達した場合、残る項目がワーカーの進行順に依存する。現状は
  診断付きで「不完全」として扱い、既存の成果物を上書きしない。有界メモリでの
  完全な走査は M7 の spill 設計と併せて解く

**実装済みの公開方式:** 内容由来の世代別不変パスと、マニフェストだけの原子的置換。
同一出力先への書き込みは排他制御し、旧世代の再利用時もチェックサムを照合する。

## M2 — C / C++ 抽出

状態: T1 / T2 とシンボル・参照候補の保存を実装済み。規模の受け入れは未完了。

- T1 行指向抽出（include、定義候補、根拠コメント）
- T2 構文抽出（型、関数、フィールド、マクロ）
- 構文解析は tree-sitter を再利用する（[設計判断](decisions.md) ADR-3 で確定済み）
- `#ifdef` 追跡と `GUARDED_BY`
- レガシー符号化の復号（[設計判断](decisions.md) ADR-9 で確定済み）

**完了条件:** `linux` コーパスでシンボル抽出が完了し、ゴールデン テストが通る。

**未了:**

- 正しい固定 SHA での `linux` 再測定、Windows での実測と両 OS の成果物一致（T-1 の 3）。
  CI の `corpus-large` ジョブで定期実行する構成にしてあり、実行できた時点で
  [性能](performance.md) へ追記する
- 過去の参考測定は `linux` で 7.95 GiB に達した。段 4 の退避と予算制御を追加したが、正しい入力での再測定は未了。
  代表合成入力でも時間の非劣化をまだ達成していない（[性能](performance.md)）。参考測定を新実装の証拠へ付け替えない

## M3 — 解決

状態: 未実装。メモリ有界化を前提とする。

- 大域シンボル表の外部ソート構築
- include 解決、呼び出し・参照・継承の解決
- 確度（`EXTRACTED` / `RESOLVED` / `AMBIGUOUS`）の付与

**完了条件:** 解決率と確度分布を計測し、`AMBIGUOUS` の内訳を説明できる。

## M4 — ストレージと照会

状態: 固定長セグメント・CSR・字句索引・JSON 照会・HTML 出力を実装済み。

- セグメント形式、CSR、文字列 blob、ID マップ
- 名前索引と n-gram 索引（CJK 対応）
- `search` / `show` / `neighbors` / `path` / `context` / `stats` / `verify`
- トークン予算と JSON 出力
- 監査・探索用の対話的な HTML 出力（`export html`）
- 管理 JSON の失敗契約、言語別の抽出集計、明示的な freshness、機械固有設定の分離、進捗表示

**完了条件:** 照会レイテンシが [性能](performance.md) の目標内。CJK 検索テストが通る。

**未了:**

- n-gram 転置索引。完全一致・前方一致は `.lookup` の二分探索で実装済み。
  部分一致は UTF-8 キー blob の有界走査であり、ノード表の全走査には退行しない
- 索引のない旧成果物は検索時に再生成を求める。旧実装の `usedIndex: false` は現行動作ではない
- 両 OS の cold / warm 計測と起動時間目標。ReadyToRun を使った macOS の T0 実コーパス測定でも
  起動のみで約 52 ms、p50 ≤ 50 ms は未達（[性能](performance.md) 5.1）。配布形態を継続評価する
- Int32 上限を超える論理セグメント。物理的な 128 MiB 分割は実装したが、論理オフセットの上限は残る

## M5 — 増分更新

状態: 未実装。世代単位の原子的公開とは別の機能。

- 変更検出、tombstone、デルタ セグメント、コンパクション
- 改名・移動の検出
- 影響範囲に限定した再解決

**完了条件:** 増分等価性テスト（T-2）が通り、増分更新の目標時間を満たす。

## M6 — 解析と補強

状態: 未実装。`context` の有界な近傍取得は M4 で提供済み。

- 中心性、コミュニティ検出、決定的なコミュニティ命名
- ビルド記述、`Kconfig`、`OWNERS` / `MAINTAINERS`、git 共変更
- `explain` / `impact` / `context`

**完了条件:** コミュニティ分割が決定的に再現し、ハブ検出が機能する。

## M7 — 規模検証

状態: 一部の macOS 測定記録あり。T2 全体・両 OS・cold cache の受け入れは未完了。

- 退避・外部ソート・物理分割の基礎を実装。全パイプラインの有界化と非劣化の検証を M3 / M5 に先行する
- `chromium` コーパスでの完全インデックス
- メモリ上限、所要時間、生成物サイズの実測
- [性能](performance.md) に目標と実測を並べ、達成・未達・未測定を区別する

**完了条件:** `chromium` のインデックス生成と照会が目標内で完了する。達成できない場合は原因を特定し、目標または設計を改訂する。

## M8 — 多言語対応の拡大

- Rust、Python、JavaScript / TypeScript
- 続いて Java、Go、C#、F#、Objective-C / Objective-C++

構文解析は tree-sitter を再利用するため、言語の追加は `native/sources.json` への
項目追加と、言語ごとの抽出規則（どのノード種別を何のノードにするか）の実装になる。
文法そのものの実装は不要である。

**完了条件:** 各言語のゴールデン テストが通り、既存言語の性能に回帰がない。

## M9 — 公開準備

- MCP アダプター（標準入出力のみ）
- `SECURITY.md`、`CONTRIBUTING.md`、配布形態の確定
- 利用者向けドキュメントの整備

## 未決事項

[設計判断](decisions.md) の未決事項に加え、次を解決する必要がある。

| 項目 | 決着させる時期 |
| --- | --- |
| 内容ハッシュの SIMD 化が必要か（[性能](performance.md) 5.1 の実測に基づく） | M7 |
| セグメントの分割ビュー読み取り（2 GiB 超のセグメント） | M4 |
| 生成物の配布形態（Native AOT / 単一ファイル / フレームワーク依存） | M7 |
| 複数リポジトリ統合の生成物単位 | M6 |
| コミュニティ命名の品質が実用に足るか。足りない場合の代替（LLM は使わない前提での改善） | M6 |
| 既定で同梱する文法の範囲（成果物サイズとの兼ね合い） | M8 |
| 全文検索を将来的に別コンポーネントとして持つか | M9 以降 |
| 大規模コーパスを CI で回すための実行基盤（ホスト型ランナーの制限に収まるか） | M7 |
