# 要件

## 1. 目的

対象リポジトリの構造を決定的に解析してナレッジ グラフを構築し、AI コーディング エージェントが必要最小限の文脈だけを取得できるようにする。グラフ生成に AI を使わないことで、グラフ構築の AI コストをゼロにする。

## 2. スコープ

本書は最終的な要件を示す。現行の実装状況は [ロードマップ](roadmap.md) に分けて記録する。
未実装の機能や規模目標を、現在の CLI が保証するものとして扱わない。

### 2.1 対象

- ローカル ファイルシステム上のソース ツリー（git 作業ツリーを含む）
- 単一リポジトリ、および複数ルートの統合グラフ
- Chromium、Linux カーネル規模の超大規模リポジトリ

### 2.2 範囲外

以下は明示的に作らない。将来的に必要になった場合も、別コンポーネントとして分離する。

| 範囲外 | 理由 |
| --- | --- |
| LLM 推論 | 本プロジェクトの存在理由が AI コスト削減であるため |
| 埋め込みベクトル、意味的類似検索 | モデル配布・実行が必要になり、決定性と軽量性を損なう |
| 自然言語の意味理解 | 字句一致と構造探索で代替する（[クエリ仕様](query-and-cli.md)参照） |
| 対象リポジトリのビルド実行 | 任意コード実行になり、脅威モデルを破壊する |
| コード生成、リファクタリング適用 | 読み取り専用ツールとして境界を保つ |
| ネットワーク通信、テレメトリ | ローカル完結を保証するため |
| IDE 拡張、常駐 GUI アプリ | CLI と JSON を一次界面とする。監査用の静的・オフライン HTML 出力は FR-5 の範囲 |

## 3. 機能要件

### FR-1 インデックス生成

- ソース ツリーを走査し、ファイル・ディレクトリ・シンボル・ビルド ターゲット・所有者・根拠コメントをノード化する
- `.gitignore` および `.srcnetignore` を尊重する。無視設定はディレクトリ単位で階層的に適用する
- 走査ルート配下では、名前が `.` で始まるディレクトリとその配下を、階層や無視設定にかかわらず除外する。ファイル名が `.` で始まるだけでは除外しない
- 生成物はリポジトリ外の任意ディレクトリにも出力できる（既定は `<repo>/.srcnet/`）

### FR-2 関係の解決

- include / import、呼び出し、継承、実装、オーバーライド、型参照、テスト対象、ビルド依存、構成ガード、所有、共変更をエッジとして生成する
- 各エッジに確度（`EXTRACTED` / `RESOLVED` / `AMBIGUOUS`）を付与し、根拠を追跡可能にする
- 詳細は [グラフ モデル](graph-model.md) と [抽出](extraction.md) を参照

### FR-3 増分更新

- 内容ハッシュが変化したファイルのみ再抽出する
- 削除・改名・移動を検出し、グラフから正しく反映する
- 増分更新の結果は、同じ最終状態に対する完全再構築と論理的に等価でなければならない

### FR-4 解析

- 次数中心性、PageRank、媒介中心性の近似を決定的に計算する
- コミュニティ検出を固定シードで実行し、実行ごとに同じ分割を返す
- コミュニティ名を LLM ではなく、パス共通接頭辞と識別子の語彙統計から決定的に生成する

### FR-5 照会

- シンボル・パス・テキストの検索、近傍探索、最短経路、影響範囲、説明、統計を提供する
- 出力はトークン予算を指定でき、予算超過時は決定的な優先順で切り詰め、切り詰めた事実を明示する
- 人間可読のテキストと、スキーマ版付きの JSON の両方を出力できる
- 人間による監査用に、有界な部分グラフを単一のオフライン HTML として出力できる

### FR-6 検証

- 生成物の整合性（形式版、チェックサム、参照の閉包）を検査するコマンドを提供する
- 同一入力から二度生成し、バイト単位の一致を確認できる

## 4. 非機能要件

[開発規約](../.github/instructions/fsharp-dotnet.instructions.md) の必須非機能要件に従う。本節はそれを srcnet の文脈に具体化したもので、規約が上位にある。

| ID | 要件 | 検証方法 |
| --- | --- | --- |
| NFR-1 | macOS と Windows の両方で同一の外部仕様で動作する | 両 OS の CI で全テストと成果物起動を検証（[テスト](testing.md)） |
| NFR-2 | 既知の不具合ゼロで完了する | 単体 / 統合 / 回帰 / property / fuzz テストと静的解析 |
| NFR-3 | セキュリティ リスクを残さない | 脅威モデルに沿った検証（[セキュリティ](security.md)） |
| NFR-4 | CJK 入力で正しく動作する | CJK コーパス テスト（[移植性と国際化](platform-and-i18n.md)） |
| NFR-5 | クラッシュ・フリーズを起こさない | stress / 並行 / 長時間 / 異常系テスト |
| NFR-6 | 大容量ファイル処理が高速である | 大容量ベンチマーク（[性能](performance.md)） |
| NFR-7 | システム リソース使用が最適化されている | RSS / CPU / handle / I/O の予算検証 |
| NFR-8 | レスポンスが迅速である | 起動時間と p50 / p95 / p99 レイテンシ計測 |
| NFR-9 | 検索処理が高速である | 検索ベンチマーク（CJK 含む） |

### 4.1 srcnet 固有の追加要件

| ID | 要件 |
| --- | --- |
| NFR-10 | **AI 不使用**: 製品コードにモデル推論、埋め込み生成、外部 API 呼び出しを含まない。ネットワーク I/O を行わない |
| NFR-11 | **決定性**: 同一入力・同一バージョンから、OS と並列度によらずバイト単位で同一の成果物を生成する |
| NFR-12 | **メモリ有界性**: ピーク RSS を入力規模に依存しない上限内に収める。既定上限は設定可能とする |
| NFR-13 | **中断可能性**: すべての長時間処理は取り消し可能で、中断しても生成物を破損させない |
| NFR-14 | **前方互換**: 生成物に形式版を持ち、非互換な版を安全に検出して拒否する |

## 5. 規模目標

Chromium と Linux カーネルを「動作確認しなければならない上限」として扱う。以下は設計の前提となる概算であり、実測で確定させる。

| 指標 | Linux カーネル（概算） | Chromium（概算） |
| --- | --- | --- |
| ファイル数 | 約 10 万 | 約 50 万 |
| 行数 | 数千万行 | 数千万行 |
| 想定ノード数 | 10^6 〜 10^7 | 10^7 〜 10^8 |
| 想定エッジ数 | 10^7 〜 10^8 | 10^8 〜 10^9 |

この規模では全件を一度に復号・常駐させないことが必要になる。保存形式の一般的な優劣を
断定せず、固定長セグメントと CSR の設計を代表 workload で検証する（[ストレージ](storage.md)、[設計判断](decisions.md)）。

## 6. 受け入れ基準

次をすべて満たしたときに、当該マイルストーンを完了とみなす。

1. macOS と Windows の両方で Release ビルド、全テスト、成果物起動が成功する
2. 対象コーパスに対する完全インデックスが、[性能](performance.md) の予算内で完了する
3. 同一コーパスを二度インデックスし、成果物がバイト単位で一致する
4. 増分更新を含むマイルストーンでは、更新の結果が完全再構築と論理的に等価である
5. 製品バイナリの依存閉包にネットワーク クライアントとモデル ランタイムが含まれない
6. CJK コーパスで文字化け・欠落・クラッシュが発生しない
7. 既知の未修正不具合とセキュリティ指摘がゼロである
