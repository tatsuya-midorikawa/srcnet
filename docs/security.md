# セキュリティ

## 1. 脅威モデル

### 1.1 前提

srcnet は**信頼できない入力**を扱う。利用者は自分が書いていないリポジトリ（クローンした OSS、依存ライブラリ、third_party）を解析する。攻撃者はリポジトリの内容を完全に制御できると仮定する。

### 1.2 資産

| 資産 | 保護目標 |
| --- | --- |
| 利用者のマシンとファイルシステム | 対象リポジトリからの任意コード実行・書き込みを防ぐ |
| 利用者のソースコード | 外部へ送信されないことを保証する |
| 生成物の完全性 | 破損・改竄を検出できる |
| 可用性 | 悪意ある入力でクラッシュ・ハングしない |

### 1.3 信頼境界

```text
[対象リポジトリの内容]  ← 信頼しない
        │
        ▼
[srcnet プロセス]      ← 信頼する。ただし入力を検証する
        │
        ▼
[生成物 .srcnet/]      ← srcnet が生成したものとして信頼する
        │
        ▼
[AI エージェント / 端末] ← 出力の安全性は srcnet が責任を持つ
```

## 2. 統制

### C-1 任意コード実行の排除

- 対象リポジトリのビルドを実行しない。`make`、`gn`、`cmake`、`npm` などを起動しない
- 対象リポジトリからスクリプト、実行可能ファイル、共有ライブラリ、構文解析文法を**読み込まない**。
  構文解析には tree-sitter を再利用するが、読み込む文法は srcnet 自身が構築した固定の一覧に限る。
  tree-sitter は文法を外部の共有ライブラリとして読み込む使い方もできるが、その経路は採らない
- 抽出器のプラグイン機構を、対象リポジトリ由来の設定から動的に読み込む形で実装しない（[アーキテクチャ](architecture.md) 4）
- ビルド記述（`BUILD.gn`、`Makefile` 等）は**データとして解析**するのみで、評価・実行しない

これは機能上の制約でもある。ビルド構成を実行すれば精度は上がるが、脅威モデルを破壊するため採らない。

### C-2 ネットワーク遮断

- 製品コードの依存閉包に HTTP クライアントおよびネットワーク クライアントを含めない
- テレメトリ、使用状況収集、更新確認を行わない
- この不変条件は「依存閉包の検査」としてテストで自動検証する（[テスト](testing.md)）

MCP サーバー モードを追加する場合も、既定は標準入出力経由とし、ネットワーク待ち受けは行わない。

### C-3 パス トラバーサル対策

- 走査対象をルート配下に限定する。シンボリック リンクによるルート外への脱出を拒否する
- 包含判定は**正準化したパス同士**で行う。リンクの解決 API は最終要素しか解決しないため、
  経路の途中にあるリンクを解決しないままでは、ルート内のリンクを中継した名前が
  文字列上はルート内に見え、ルート外の内容を読めてしまう。解析ルートも同じ正準形へ揃える
- 無視ファイル（`.gitignore` / `.srcnetignore`）は、**通常エントリと同じ順序で**属性・リンク・実体パスを検証してから開く。
  先に開くと、リンクを追跡しない設定でもルート外のファイルを読み、その内容で索引対象を操作される
- 出力先パスは利用者が明示したもののみを使う。対象リポジトリの内容から出力先を決定しない
- 既定の出力先 `.srcnet` は**対象リポジトリの中にある**。出力ルートから管理対象ファイルまでの各要素について、
  シンボリック リンク・junction・その他の reparse point を拒否する。拒否しなければ、索引するだけで
  リンク先の任意ファイルを上書き・再帰削除できる
- 一時ファイルは既存の項目を追跡せず排他的に新規作成する。`FileMode.Create` は既存のリンク先を上書きしてしまう
- 生成物のファイル名に対象リポジトリ由来の文字列を使わない

### C-4 リソース枯渇対策

悪意ある、あるいは単に巨大な入力に対して、資源消費を有界に保つ。NFR-5（クラッシュ・フリーズなし）と NFR-7（リソース最適化）に直結する。

| 攻撃 / 状況 | 対策 |
| --- | --- |
| 巨大な単一ファイル | ファイルあたりの処理上限を設け、超過は診断付きでスキップ |
| 極端に深いディレクトリ階層 | 深さ上限とリンク循環検出 |
| 極端に長い 1 行、極端に深い入れ子構文 | 走査・解析に深さと長さの上限を設ける |
| 病的な正規表現の実行時間爆発 | 入力依存のバックトラッキングを持つ正規表現を使わない。手書き走査または線形時間の照合を使う |
| ファイル数の爆発 | 走査は有界メモリで動作し、件数上限に達したら診断して継続 |
| 大量の解決候補 | 候補数に上限を設け、超過分は要約する |
| 巨大な無視ファイル | 規則数・総バイト数・1 行の長さのそれぞれに上限を設け、到達時点で読み取りを止める。読み取りは取り消し可能にする |
| FIFO・ソケット・デバイス | 通常ファイルと managed API では区別できず、`open` が無期限に blocking して取り消しも効かない。サイズ 0 のファイルは開かず、結果を開かずに決定する |

### C-5 出力の無害化

**対象リポジトリの内容がそのまま端末や AI エージェントへ流れる**ため、出力は無害化が必要である。

- ファイル名・識別子・コメントに含まれる ANSI エスケープ シーケンスと制御文字を、端末出力時に無害化する。これを怠ると、リポジトリ側から端末表示を偽装できる
- JSON 出力では制御文字を適切にエスケープする
- 出力に含めるソース抜粋は、既定で行範囲のみとし、本文は明示的な指定時のみ含める

### C-6 生成物の完全性

生成物は**破損しているか、悪意をもって改変されている可能性がある外部入力**として扱う。

- マニフェストに各セグメントのチェックサムを保持し、読み込み時に検証する
- 形式版が非互換な生成物は、読まずに明示的に拒否する
- 破損を検出した場合は、部分的に読み進めず失敗させる
- セグメント名は `segments/<generation>/<name>` の形だけを受け入れ、絶対パス、親参照、UNC、
  区切りの混在、代替データ ストリームを拒否する。結合後の実体が成果物ルート配下にあること、
  経路の各要素がリンクでないことも確かめる。`verify`、`stats`、将来の reader は同一の変換を使う
- JSON の値種別、必須性、数値範囲、型固有のセグメント不変条件（件数、レコード長、payload 長、
  オフセット範囲）を検証してから領域型へ変換する。narrowing conversion は checked にする
- 想定内の破損は未処理例外ではなくドメイン エラーにする。利用者が「非互換・破損」と実装不具合を
  区別できなければならない

### C-7 秘匿情報の扱い

- srcnet 自身は資格情報を必要とせず、保持しない
- 生成物にはソースの識別子とコメント抜粋が含まれる。対象リポジトリに秘匿情報が含まれる場合、生成物にも波及し得る
- `.srcnet/` を版管理へ含める場合の情報漏えいリスクを、ドキュメントで明示的に警告する
- ログに対象リポジトリの内容を無制限に出力しない

## 3. 依存関係

- 製品コードへの新規 NuGet 追加は原則禁止（[開発規約](../.github/instructions/fsharp-dotnet.instructions.md)）。攻撃面の観点からもこれを維持する
- ネイティブ ライブラリを採用する場合は、供給元、更新体制、既知脆弱性、メモリ安全性を評価し、[設計判断](decisions.md) に記録する
- 依存の脆弱性検査を CI で継続的に実行する

### 3.1 tree-sitter

構文解析器として tree-sitter を再利用する（[設計判断](decisions.md) ADR-3）。唯一のネイティブ依存であり、次の統制を置く。

| 項目 | 扱い |
| --- | --- |
| 取得元と版 | `native/sources.json` に取得元・版・SHA-256 を固定する。検証に失敗した取得物は使わない |
| 取得経路 | 構築時のみ。製品の実行時にネットワーク通信は行わない |
| 展開 | 書庫の項目名が展開先の外を指すもの、リンクを含むものを拒否する |
| 文法の選択 | コンパイル時に固定した一覧。対象リポジトリから読み込む経路を持たない |
| メモリ安全性 | 相互運用の境界で寿命・範囲・null を検証する。ノードは所属する木より長く生存できず、バイト範囲は必ずソース長に収める |
| 資源上限 | ファイルあたりの解析時間に上限を設け、取り消しフラグを伝播する |
| 不在時 | 共有ライブラリが無い環境では構文解析を利用不可として扱い、構造グラフの生成は続行する |

## 4. メモリ安全性

性能のために `Span`、`stackalloc`、ポインタ、memory mapping を用いる箇所がある。これらは NFR-3 の観点で最も危険な領域である。

- 境界検査を省く最適化は、不変条件を証明できる場合に限る。証明を伴わない省略を行わない
- 未検証の外部入力から算出した値を、境界検査なしにオフセットや長さとして使わない
- ネイティブ相互運用の境界で、長さ・範囲・整列・寿命を検証する
- 該当箇所には fuzz テストを必須とする（[テスト](testing.md)）

## 5. 独自実装を避ける領域

性能を理由にしても、次を自作しない。

- 暗号プリミティブ、署名、乱数生成
- 認証・認可プロトコル

内容ハッシュは暗号学的用途ではなく変更検出用途だが、検証済みの platform 実装（BCL の `SHA256`）を使う（[設計判断](decisions.md) ADR-8）。ただし、生成物の完全性検証に用いる場合の要件は別途明記する。

## 6. 脆弱性の報告

報告手順は公開時に `SECURITY.md` として整備する（[ロードマップ](roadmap.md)）。
