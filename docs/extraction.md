# 抽出

## 1. 方針

抽出は「完全な意味解析」を目指さない。コンパイラを再実装せずに、AI エージェントの質問に答えるのに十分な構造を、規模に耐える速度で取り出す。精度と速度の妥協点は段階（tier）で明示する。

## 2. 段階的抽出

| 段階 | 内容 | コスト | 適用 |
| --- | --- | --- | --- |
| T0 | パス、サイズ、内容ハッシュ、言語判定 | 極小 | 全ファイル |
| T1 | 行指向走査による import / include、定義らしき行、根拠コメント | 小 | 全テキスト ファイル |
| T2 | 構文解析による定義・参照・呼び出し・継承の構造抽出 | 中 | 対応言語 |
| T3 | ビルド構成に基づく高精度解決（`compile_commands.json`、`BUILD.gn`、`Kconfig`） | 大 | 明示的に有効化した場合 |

既定は T2 まで。T3 は Chromium のような「ビルド構成なしでは正確に解けない」対象向けに任意で有効化する。
ただし現行の T3 は未実装で、CLI は指定を拒否する。

T1 は T2 の代替ではなく前段である。構文解析器の不在・未対応言語でも T1 を試み、
ファイルの構造ノードは残す。符号化の曖昧さ、サイズ・時間・件数の上限などでは抽出を見送り、
診断とフラグを残すため、すべての入力で T1 のシンボルが得られるわけではない。

## 3. 言語対応

### 3.1 優先順位

目標リポジトリから逆算する。

| 優先度 | 言語 | 根拠 |
| --- | --- | --- |
| P0 | C, C++ | Linux カーネルと Chromium の本体 |
| P0 | ビルド記述（`BUILD.gn`, `Kbuild`/`Makefile`, `Kconfig`, `CMakeLists.txt`） | 目標リポジトリの構造把握に必須 |
| P1 | Rust, Python, JavaScript / TypeScript | Chromium の周辺と一般的なリポジトリ |
| P1 | 所有情報（`OWNERS`, `MAINTAINERS`） | 大規模リポジトリでの責任範囲 |
| P2 | Java, Go, C#, F#, Objective-C / Objective-C++ | 一般的な適用範囲の拡大 |
| P3 | その他 | T1 のみで対応 |

### 3.2 構文解析の実装方針

T2 以降の構文解析には **tree-sitter を再利用する**（[設計判断](decisions.md) ADR-3）。対応言語の数が要件である以上、言語ごとに構文解析器を自作する費用は現実的でないためである。T1 の行指向抽出は引き続き自前で行い、tree-sitter に依存しない。

構文解析器が満たすべき条件は次のとおりで、tree-sitter はいずれも満たす。

- 対象リポジトリ由来のファイルを実行しない。文法・プラグインを対象リポジトリから動的に読み込まない
- 構文エラーを含むファイルでも部分的な結果を返し、クラッシュしない
- 入力サイズに対して線形に近い時間で動作し、病的な入力で指数的に劣化しない
- macOS と Windows の両方で同一の結果を返す

実装上の約束は次のとおり。

| 項目 | 扱い |
| --- | --- |
| 同梱する文法 | C, C++, Python, Rust, Go, Java, JavaScript, C#, TypeScript, TSX, F#。`native/sources.json` に取得元・版・SHA-256 を固定する。一覧はコンパイル時に確定し、対象リポジトリからは読み込まない |
| 文法が別になる拡張子 | `.tsx` は JSX を含むため `tsx` 文法を使い、言語も `Tsx` として区別する。`.fsi` は本体と同じ `fsharp` 文法で解析し、言語だけ `FSharpSignature` として区別する（C/C++ のヘッダーと同じ扱い） |
| 言語の追加 | `native/sources.json` への項目追加と、言語ごとの抽出規則の実装。文法自体の実装は不要 |
| 上限 | ファイルあたりの解析時間に上限を設け、取り消しを伝播する |
| 相互運用の安全性 | ノードは所属する木より長く生存できず、バイト範囲は必ずソース長に収める |
| 解析器が無い環境 | 構文解析を利用不可として扱い、T0（構造）と T1（行指向）の結果は変わらず得られる |

構文解析器の有無で成果物が変わるため、`manifest.json` は要求段階、解析器の可用性、
コンパイル時に固定した文法一覧を記録する。文法一覧は構築候補であり、
実際に同梱したサブセットや全言語の T2 抽出対応を意味しない。T2 のグラフ抽出は現在 C / C++ である。
`options.requestedTier` と到達段階の `options.tier` は分けて保持する。
解析器の一部だけを構築した場合も、要求した C / C++ の文法がなければ
言語ごとに縮退を診断する。別言語の文法があるだけで完全な T2 と報告しない。

## 4. C / C++ 固有の扱い

目標リポジトリの中心であるため、方針を明示する。

### 4.1 プリプロセッサ

完全なプリプロセス展開は行わない。代わりに次を行う。

- `#include` は文字列として抽出し、解決は 5.2 の規則で行う
- `#ifdef` / `#if defined(...)` のネストを追跡し、その内側で定義されたシンボルに条件を属性として付ける。同時に `GUARDED_BY` エッジを生成する
- 条件分岐は**すべての枝を抽出対象とする**。特定の構成を仮定して枝を捨てると、別構成でのグラフが欠落するため
- 関数形式マクロは `Macro` ノードとして持ち、展開はしない。マクロ経由の呼び出しは `AMBIGUOUS` になり得る

### 4.2 宣言と定義

ヘッダーの宣言は `DECLARES`、実装の定義は `DEFINES` として別エッジにする。呼び出し解決は定義側を優先し、定義が見つからない場合のみ宣言へ張る。

### 4.3 include の解決

以下は M3 / T3 の計画である。現行は include を参照候補として記録し、ファイル間エッジへは解決しない。

1. 引用形式 `#include "x.h"` は、まず同一ディレクトリからの相対で解決する
2. 山括弧形式 `#include <x.h>` と 1 で解決できなかったものは、include パス候補集合に対して解決する
3. 候補が複数ある場合は `AMBIGUOUS` とし、決定的な優先順（パスの近さ、次に辞書順）で並べる
4. T3 を有効にした場合は、`compile_commands.json` の include パスを使って一意化する

## 5. シンボル解決

本節は M3 の計画であり、現行は `.refs` に未解決候補を保存するところまでを実装している。

### 5.1 大域シンボル表

段 4 の出力を集約し、`(言語, 修飾名, 種別)` をキーとする表を構築する。表は規模目標のため常駐させず、外部マージ ソートで構築してセグメント化する。

### 5.2 解決規則

参照は次の順で解決し、最初に一意に定まった段階で確定する。

1. 同一スコープ（関数内、クラス内）
2. 同一ファイル
3. 同一翻訳単位（include 閉包）または同一モジュール
4. 同一ディレクトリ
5. リポジトリ全体で修飾名一致
6. リポジトリ全体で短い名前一致

1 〜 4 で一意に決まったものを `RESOLVED`、5 で一意ならば `RESOLVED`、6 に到達したものや複数候補が残ったものを `AMBIGUOUS` とする。段階の番号は根拠として保持し、照会時に提示できる。

### 5.3 解決しないもの

次は原理的に静的解決できないため、`AMBIGUOUS` として候補を列挙するに留める。推測で単一の答えを出さない。

- 仮想関数呼び出しの実際の解決先
- 関数ポインタ、コールバック経由の呼び出し
- 動的ディスパッチ、リフレクション
- マクロ生成コード内の呼び出し

## 6. 補強（コード外の情報源）

下表のうち、現行 T1 が持つのは一部ビルドターゲット・構成シンボル・根拠コメントの候補である。
所有情報・git 共変更・ビルド依存の解決は M6 の計画とする。

| 情報源 | 生成物 |
| --- | --- |
| `BUILD.gn` / `Kbuild` / `Makefile` / `CMakeLists.txt` | `BuildTarget` ノード、`BUILT_FROM` / `BUILD_DEPENDS` エッジ |
| `Kconfig` | `ConfigSymbol` ノード、`GUARDED_BY` エッジ |
| `OWNERS` / `MAINTAINERS` | `Owner` ノード、`OWNED_BY` エッジ |
| git 履歴 | `CO_CHANGED` エッジ（同一コミットでの共変更頻度を重みに） |
| 根拠コメント | `Note` ノード、`EXPLAINS` エッジ |

git 履歴の走査は既定で直近 N コミットに制限する。Linux カーネルの全履歴を無制限に走査すると、インデックス時間が本体解析を上回るため。

## 7. テスト検出

現行はパス・ファイル名の規則に加え、Google Test の `TEST` / `TEST_F` などからテストの
フラグと未解決の `TESTS` 参照候補を生成する。対象シンボルへのエッジ解決と、
それ以外の言語固有テスト属性への拡大は今後の範囲である。命名規約から対象を推定する
場合は `AMBIGUOUS` とし、推測を確定として扱わない。

## 8. 生成コードとベンダー コード

Chromium の `third_party/` や生成コードは、量が本体を上回ることがある。

- 既定で `third_party/`、`node_modules/`、`vendor/`、`out/` などを候補として検出し、`vendored` フラグを付ける
- 除外はしない。除外すると依存が切れるため、フラグ付きで保持し、既定の照会結果では順位を下げる
- 生成コードは、生成物マーカー コメント（`DO NOT EDIT` など）とパス規則で検出し `generated` フラグを付ける
