# グラフ モデル

本書は最終的な語彙と設計を示す。現行の Writer が永続化するエッジは
`CONTAINS` / `DECLARES` / `DEFINES` / `GUARDED_BY` で、呼び出し・参照・継承などは
未解決候補として `.refs` に保存する。`Owner` / `Community`、解析属性、複数ルートの統合は未実装である。

## 1. ノード種別

| 種別 | 説明 | 主な生成元 |
| --- | --- | --- |
| `Repository` | 解析ルート | 走査 |
| `Directory` | ディレクトリ | 走査 |
| `File` | ファイル | 走査 |
| `Module` | 名前空間、パッケージ、モジュール | 抽出 |
| `Type` | class / struct / interface / enum / union / trait | 抽出 |
| `Function` | 関数、メソッド、コンストラクタ | 抽出 |
| `Field` | メンバー変数、プロパティ | 抽出 |
| `Variable` | グローバル変数、静的変数 | 抽出 |
| `Constant` | 定数、定数マクロ | 抽出 |
| `Macro` | 関数形式マクロ | 抽出 |
| `BuildTarget` | `BUILD.gn`、`Kbuild`、`CMakeLists.txt` 等のターゲット | 補強 |
| `ConfigSymbol` | `Kconfig` シンボル、ビルド フラグ | 補強 |
| `Owner` | `OWNERS` / `MAINTAINERS` のエントリ | 補強 |
| `Note` | `TODO:` `FIXME:` `NOTE:` `HACK:` `SAFETY:` などの根拠コメント | 抽出 |
| `Community` | 検出されたコミュニティの集約ノード | 解析 |

`BuildTarget` と `ConfigSymbol` は Chromium と Linux カーネルを主目標に据えたことから来る。この 2 つのリポジトリでは、ビルド グラフと構成フラグを持たない限り「このコードは実際に何のためにビルドされるのか」に答えられない。

## 2. エッジ種別

| 種別 | 向き | 説明 |
| --- | --- | --- |
| `CONTAINS` | 親 → 子 | ディレクトリ → ファイル、ファイル → シンボル、型 → メンバー |
| `INCLUDES` | ファイル → ファイル | C/C++ の `#include` |
| `IMPORTS` | ファイル → モジュール/ファイル | import、use、require |
| `DECLARES` | ファイル → シンボル | 宣言のみ（C/C++ ヘッダー） |
| `DEFINES` | ファイル → シンボル | 定義の実体 |
| `CALLS` | 関数 → 関数 | 呼び出し |
| `REFERENCES` | シンボル → シンボル | 呼び出し以外の参照 |
| `INHERITS` | 型 → 型 | 継承 |
| `IMPLEMENTS` | 型 → 型 | インターフェイス実装 |
| `OVERRIDES` | 関数 → 関数 | オーバーライド |
| `TYPED_AS` | フィールド/変数 → 型 | 型の使用 |
| `TESTS` | 関数 → シンボル | テストと対象の対応 |
| `BUILT_FROM` | ビルド ターゲット → ファイル | ターゲットの構成ファイル |
| `BUILD_DEPENDS` | ビルド ターゲット → ビルド ターゲット | ビルド依存 |
| `GUARDED_BY` | シンボル → 構成シンボル | `#ifdef CONFIG_X` による条件付き有効化 |
| `OWNED_BY` | ファイル/ディレクトリ → 所有者 | `OWNERS` / `MAINTAINERS` |
| `CO_CHANGED` | ファイル → ファイル | git 履歴上の共変更（重み付き） |
| `EXPLAINS` | 根拠コメント → シンボル | 設計意図の対応付け |
| `MEMBER_OF` | ノード → コミュニティ | コミュニティ所属 |

`DECLARES` と `DEFINES` を分離する点は C/C++ で本質的である。ヘッダーでの宣言と実装ファイルでの定義を同一視すると、Chromium 規模では呼び出し解決が壊れる。

## 3. 確度

すべてのエッジは確度を持つ。AI を使わない以上、解決の限界を隠さず明示することが正確性の担保になる。

| 確度 | 意味 | 例 |
| --- | --- | --- |
| `EXTRACTED` | ソースに明示的に書かれている | `#include "foo.h"`、`class B : public A` |
| `RESOLVED` | 一意な候補へ決定的規則で解決した | 同一翻訳単位内の呼び出し先 |
| `AMBIGUOUS` | 複数候補があり、規則で一意化できない | 仮想呼び出し、同名オーバーロード多数 |

M3 では `AMBIGUOUS` の候補集合と決定的な順位を保持する。現行の CSR は確度の列を持たず、
照会は構造から抽出したエッジを `EXTRACTED` として返す。`--include-ambiguous` は未実装である。
将来追加する場合も全候補を無制限に出さず、出力予算を守る。**推測を確定として出力しない**ことを不変条件とする。

## 4. ノード ID

### 4.1 要件

1. 決定的である（OS、並列度、実行時刻に依存しない）
2. 無関係な編集で変わらない（あるファイルの先頭に空行を足しても、末尾の関数の ID は変わらない）
3. 増分更新をまたいで安定する
4. 10^8 規模で衝突しない

### 4.2 定義

```text
NodeId = SHA-256(schemeVersion ‖ kind ‖ repoId ‖ normalizedPath ‖ qualifiedName ‖ ordinal)[0..16]
```

| 要素 | 正規化規則 |
| --- | --- |
| `kind` | ノード種別の安定した数値 |
| `repoId` | ルートの論理名。絶対パスは含めない |
| `normalizedPath` | リポジトリ相対、区切りは `/`、Unicode NFC |
| `qualifiedName` | 言語ごとの規則で構成した完全修飾名 |
| `ordinal` | 同一スコープ内で名前・種別が衝突する場合の序数。出現位置順で決定的に割り当てる |

ID にバイト位置や行番号を含めないのは要件 2 のためである。位置は属性として持ち、ID には使わない。

128 ビットを使うため、10^9 ノードでも衝突確率は無視できる。それでも衝突は検出し、握りつぶさず明示的な失敗として扱う。

## 5. ノード属性

| 属性 | 説明 |
| --- | --- |
| `id` | 128 ビット ノード ID |
| `kind` | ノード種別 |
| `language` | 言語 |
| `name` | 短い名前 |
| `qualifiedName` | 完全修飾名 |
| `fileIndex` | 所属ファイルの密インデックス |
| `startLine` / `endLine` | 行範囲（1 起点） |
| `startByte` / `endByte` | バイト範囲 |
| `flags` | 公開範囲、テスト、生成コード、宣言のみ、条件付き などのビット |
| `docRef` | 直前のドキュメント コメントへの参照（原文の抜粋であり、生成された要約ではない） |
| `degreeIn` / `degreeOut` | 次数 |
| `rank` | 中心性スコア |
| `communityId` | 所属コミュニティ |

`docRef` / 次数列 / `rank` / `communityId` の保存は未実装である。将来の `docRef` は
ソースの原文を指し、生成要約ではない。次数の照会は現行の CSR から計算できる。

## 6. コミュニティと中心性

本節は M6 の計画であり、現行成果物にコミュニティや中心性の値はない。

### 6.1 コミュニティ検出

固定シードの Leiden 系アルゴリズムを、固定の探索順序で実行する。解像度は設定可能とし、既定値と探索順序を成果物に記録して再現性を担保する。

巨大コミュニティ（全体の一定割合を超えるもの）は再帰的に分割する。

### 6.2 コミュニティ命名（LLM 不使用）

既存ツールはここで LLM を使うが、srcnet は決定的な規則で命名する。

1. コミュニティ内ファイルのパス最長共通接頭辞を取る
2. 接頭辞が有意（自明な `src/` などでない）なら、それを主ラベルにする
3. 併せて、コミュニティ内識別子を語分割（`snake_case`、`camelCase`、CJK は文字 n-gram）し、コミュニティ内の出現頻度をコーパス全体の頻度で正規化した上位語を副ラベルにする
4. 同点は安定した順序で解消する

結果は「`net/http` — request, header, parser」のような機械的ラベルであり、自然な散文ではない。これは意図的な割り切りで、[未決事項](roadmap.md) にも記載する。

### 6.3 ハブ ノード

次数と中心性の上位ノードをハブとして印付ける。ユーティリティ的な超ハブ（あらゆる場所から参照される基盤ヘッダーなど）はコミュニティ分割を歪めるため、分割時に除外できるようにする。

## 7. 複数リポジトリ

複数ルートの統合は M6 以降の計画である。`repoId` を ID の材料に持つが、現行の `index` は
単一ルートを扱い、照会用の `--repo` フィルターはない。統合時にはリポジトリ ID の一意性も検証する。
