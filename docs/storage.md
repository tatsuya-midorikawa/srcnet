# ストレージ

## 1. 設計制約

規模目標（10^7 〜 10^8 ノード、10^8 〜 10^9 エッジ）に向け、全件の JSON 復号と常駐を避ける。

現行は **固定長レコード + memory-mapped 読み取り + CSR 隣接表** を採る。
`.nodes` / `.files` / `.refs` は 64 バイト単位のレコード配列であり、全属性が独立した
列配列になっているわけではない。完全な列分割や他形式との比較は、実測が必要な設計判断である。

根拠と却下した代替案は [設計判断](decisions.md) の ADR-2 に記録する。

## 2. ディレクトリ構成

```text
.srcnet/
  manifest.json              形式版、生成条件、セグメント一覧、チェックサム
  .writer.lock               同時書き込みを拒否する空のロックファイル
  graph.html                 任意の監査用出力。インデックス本体ではない
  segments/
    <generation>/            世代ごとに不変。世代は内容から導く 32 桁の 16 進小文字
      <id>.nodes             固定長ノードレコード
      <id>.strings           重複排除済み UTF-8 blob
      <id>.stroffsets        文字列オフセット表
      <id>.files             ファイル表（パス、内容ハッシュ、言語、サイズ、フラグ）
      <id>.edges.<kind>      前方 CSR（オフセット表 + 隣接配列）
      <id>.redges.<kind>     後方 CSR
      <id>.idmap             ソート済み NodeId → 密インデックス
      <id>.refs              未解決の参照候補
      <id>.lookup            NFC / ケース畳み込み済みの字句辞書とノード参照
      <id>.tombstones        削除済みノードのビットマップ（後続）
  .staging/                  生成中の成果物。公開時に消える
  index/
    names                    後続の索引配置案（現行は世代内の .lookup）
    ngram                    n-gram 転置索引（後続）
  analysis/
    centrality               後続。現行の読み取り形式は未定義
    communities              後続。現行の読み取り形式は未定義
```

## 3. 形式の不変条件

| 項目 | 規則 |
| --- | --- |
| バイト順 | リトル エンディアン固定（対象は x64 / arm64 のみ） |
| 整列 | 共通ヘッダーは 64 バイト。固定長レコードも 64 バイト。CSR / lookup の内部領域は各形式の配置に従う |
| レコード | 固定長。可変長データは blob へのオフセットで参照する |
| 版管理 | 全ファイル先頭にマジック番号と形式版。非互換版は読まずに明示的に失敗する |
| 不変性 | 書き込み済みセグメントは変更しない。更新は新セグメントと tombstone で表現する |
| 原子性 | `manifest.json` の原子的差し替えを唯一の公開切替点とする |
| 世代 | セグメントは世代ごとに固有のパスへ置く。世代をまたいでパスを再利用しない |
| 信頼境界 | 成果物のパスはリンクを経由しない。セグメント名は `segments/<generation>/<name>` の形だけを受け入れる |

セグメントを不変にすることで、インデックス更新中でも照会が安全に継続でき、部分的な書き込みが既存の成果物を壊さない。

### 3.1 公開手順

読み手はマニフェストを通してのみセグメント集合を見る。したがって切替点をマニフェストの
置換 1 点に絞れば、公開の途中でも「旧世代を完全に見る」か「新世代を完全に見る」かのどちらかになる。

1. 走査前に出力先を検証して `.writer.lock` を排他的に開き、片付けが終わるまで保持する。
   同時書き込みは走査・抽出を始めずに拒否する
2. セグメントを `.staging/segments/` へ書き出す
3. 世代識別子を、セグメントの名前・長さ・チェックサムから導く
4. `.staging/segments/` を `segments/<generation>/` へ移す（旧世代はそのまま残る）
5. `manifest.json` を原子的に置き換える ← **ここが唯一の切替点**
6. 現行世代と直前の世代だけを残し、それより古い世代を片付ける。世代名ではない項目は削除しない

同じ世代が既存の場合も長さだけで正常とみなさず、チェックサムを照合する。
欠損・破損した不変パスを使用中の読み手から差し替えず、別の出力先への再索引を求める。
ロックファイルは空のまま残す。削除して新しい inode へ置き換えると排他が分断されるためである。
生成失敗や中断でも、ロックを保持したまま staging を片付けてから終了する。
ライブラリから staging / publish を直接扱う呼び出し元も `Manifest.acquireWriter` の寿命を守る。
既存ファイルの公開は `File.Replace`、最初の公開は非上書きの `File.Move` を使う。
読み手は read/write/delete の共有を許可し、Windows でも読み取り中のスナップショットを維持する。

セグメント名を世代ごとに変えるのは、旧マニフェストが新世代の同名セグメントを指してしまう
状態を作らないためである。世代識別子を内容から導くのは、同じ入力から二度生成した成果物が
バイト単位で一致するという決定性の要件（[テスト](testing.md) T-1）を保つためである。

`options.tier` は到達段階、`options.requestedTier` は要求段階である。
決定性の再生成は要求段階を使うため、T2 から T1 へ縮退した場合も同じ診断を再現する。
`requestedTier` のない旧 v3 マニフェストも読めるが、再生成に使えるのは到達段階だけなので、
過去の縮退を正確に再現するには再索引が必要になる。セグメントのレイアウトは変更しない。

直前の世代を残すのは、読み手がマニフェストを読んでからセグメントを開くまでの猶予を作るためである。
猶予だけでは連続した公開に追い越され得るため、読み手は読み取りの前後でマニフェストのバイト列を
比べ、変化していれば新しいマニフェストで読み直す。

## 4. 隣接表（CSR）

エッジ種別ごとに前方・後方の CSR を持つ。

```text
offsets: 長さ N+1 の配列   ノード i の隣接は targets[offsets[i] .. offsets[i+1]-1]
targets: 隣接ノードの密インデックス配列（昇順、決定的）
```

- 種別ごとに分けることで、「呼び出しだけを 2 ホップ辿る」ような照会が無関係なエッジを読まずに済む
- 後方 CSR を持つのは「この関数を呼んでいるのは誰か」が最も頻出する質問だからである。逆引きのたびに全走査するのは規模的に不可能
- 隣接配列は昇順に整列するため、集合演算と SIMD 走査が使える
- 確度と重みは、必要な種別についてのみ並列配列として持つ

## 5. 文字列

- 全文字列を重複排除して単一 blob に格納する。同一パス片や識別子が大量に重複するため、圧縮効果が大きい
- 参照は blob へのオフセット。ノード レコードは固定長を保つ
- 文字列は UTF-8。論理パスと検索キーは NFC に正規化し、シンボルの表示名・参照候補の原文表記とは区別する

## 6. 増分更新

以下は M5 の設計案であり未実装である。現行の `index` は毎回完全生成する。
世代管理と原子的公開があることは、変更ファイルだけを再抽出できることを意味しない。

### 6.1 変更検出

1. 内容ハッシュ（SHA-256、[設計判断](decisions.md) ADR-8）の一致を基準とする
2. `(サイズ, 更新時刻)` の一致だけでは変更なしと確定しない。同サイズの上書きや保存時刻の復元を見逃すためである
3. メタデータの高速パスを追加するなら、増分等価性を損なわない条件と失効規則を先に定義する

現行のファイルレコードに更新時刻はなく、`--rehash-all` もまだ提供しない。

### 6.2 更新手順

1. 変更・追加ファイルのみ再抽出する
2. 削除・変更されたファイルに属する旧ノードを tombstone で無効化する
3. 新しい事実をデルタ セグメントとして書き出す
4. 影響を受けたエッジのみ再解決する。影響範囲は既存の逆引きエッジから決定する
5. マニフェストを原子的に差し替える

### 6.3 コンパクション

デルタ セグメントが閾値を超えたら、複数セグメントを統合し tombstone を物理削除する。統合は完全再構築と論理的に等価な結果を生まなければならず、これはテストで検証する（[テスト](testing.md)）。

### 6.4 改名の扱い

改名は「削除 + 追加」ではなく、内容ハッシュ一致による移動として検出する。パスは ID の構成要素であるため ID は変わるが、移動元との対応を記録し、履歴由来のエッジを引き継ぐ。

## 7. 索引

### 7.1 名前索引

現行の Writer は世代内に `.lookup` を生成する。名前・修飾名・論理パスを NFC キーの
順序付き辞書へまとめ、完全一致と前方一致を二分探索する。ケース畳み込み済みの辞書も同じ
セグメントへ持つ。検索は読み取り専用であり、索引のない旧成果物を自動更新したり、
ノード表の全走査へ退行したりしない。再索引が必要なことを明示的に返す。

`.lookup` は共通 64 バイトヘッダーの種別 8（`LexicalLookup`）で、索引内部の形式版は 1。
整数はリトルエンディアンであり、ヘッダーの主要件数はキー数、従属件数は posting 数である。

| 領域 | 形式 |
| --- | --- |
| 32 バイト前置き | 形式版、ノード数、ファイル数、元文字列数（各 u32）、blob 長（u64）、通常キー数、予約（各 u32） |
| 24 バイトキー | blob 内オフセット（u64）、UTF-8 長、posting 開始・件数、予約（各 u32） |
| 8 バイト posting | 密ノード番号、照合対象（各 u32。0=名前、1=修飾名、2=パス） |
| UTF-8 blob | 通常 NFC キーの後に NFC ケース畳み込みキー。各辞書は `StringComparer.Ordinal` 順 |

キーと posting の領域は隙間なく並べ、末尾の余剰データを認めない。元のノード・ファイル・
文字列表の件数と照合し、アクセスする範囲、参照先、UTF-8、整列順を検証する。キー上限は
1 MiB、検索結果は 50000 ノード、候補と posting の処理は各 200000 件に制限する。

構築中の posting は文字列参照番号・ノード番号・対象番号の 3 整数で保持する。
畳み込み済み辞書は参照番号のビット反転で区別し、正規化で同じキーになった別参照も
文字列順で併合する。これは作業メモリだけの変更で、上表のオンディスク形式は変えない。

### 7.2 部分一致索引

現行は `.lookup` の UTF-8 キー blob を mmap 上で走査する。SIMD 対応の部分列検索を使い、
一致した位置の所属キーだけを確認する。キー間をまたぐ偽一致や、UTF-8 scalar を分断した
窓境界を認めない。文字列辞書全件の復号やノード表の走査は行わない。バイト作業量の上限は
256 MiB とし、件数・作業量の上限に達した場合は省略件数が下限であることを明示する。

M4 の残項目として n-gram 転置索引を追加する。文字種によって n を変える。

| 文字種 | n | 理由 |
| --- | --- | --- |
| ラテン文字・数字・記号 | 3 | 一般的なトライグラムの選択性が十分 |
| CJK 表意文字・仮名・ハングル | 2 | CJK は 2 文字で語を成すことが多く、3 では再現率が落ちる |

n-gram は Unicode スカラー値の列に対して構成する。UTF-16 コード単位や UTF-8 バイト単位で切ると、CJK と絵文字で不正な境界が生じる。

転置リストはビットマップまたはソート済み差分符号で保持し、集合積を SIMD で処理する。

### 7.3 索引の範囲

v1 では**識別子・シンボル名・パス**を索引対象とし、全文検索は対象外とする。数千万行の全文索引は規模と目的が別問題であり、必要になった時点で別途設計する（[ロードマップ](roadmap.md)）。

## 8. memory-mapped I/O

読み取りは既定で memory mapping を使う。適用条件と検証項目は [開発規約](../.github/instructions/fsharp-dotnet.instructions.md) の該当規則に従い、加えて次を守る。

- view と handle の寿命を明示的に管理し、`use` で確実に解放する
- 対象ファイルの切り詰めによる致命的シグナル（macOS の `SIGBUS`、Windows のページ エラー）は .NET では捕捉できない。したがって **自分が生成した不変セグメントのみを mmap し、外部が更新し得る対象リポジトリのファイルは通常の読み取りで扱う**
- 32 ビット アドレス空間は対象外とする。64 ビットのみを支援する
- mmap と通常 I/O は同一 workload でベンチマークし、優位性を実測で確認してから採用する

`Query.GraphView` の値アクセサーは、アクセスしたデータの破損を `QueryException` で明示し、
空文字列やダミーノードへ置き換えない。CLI はこの型を境界で診断へ変換し、HTML は既存出力を
保持したまま失敗する。完全なチェックサム検査は `verify` が担当する。
マニフェストは種別ごとの件数合計と前方・後方 CSR の対応を検証し、隠れたエッジを
「完全な空結果」として返さない。`verify` は lookup がある場合、検索の作業上限を適用せず、
全キー・posting・参照元との一致・通常/ケース畳み込み双方の完全な網羅性まで検証する。
lookup の有無にかかわらずノード・ファイル・参照候補の言語、フラグ、位置、確度、段階と
種別件数を検証する。CSR は範囲内であるだけでなく、各行の厳密な昇順と
前方・後方が互いの転置であることを確認する。転置確認は mmap 上の二分探索で行い、
グラフ全体の複製を作らない。

近傍はノード数 200000、探索エッジ数 400000 の安全上限を持つ。指定深さは照会条件であり、
その外側は省略件数に含めない。安全上限による未探索とは区別する。双方向最短経路探索は
実際の有向エッジを保持し、上限で経路の有無を確定できない場合は完全な「経路なし」を返さない。

## 9. 成果物の扱い

- `.srcnet/` を版管理へ含めるかは利用者の選択とする。含める場合、成果物にはソースの抜粋が含まれ得ることを警告する（[セキュリティ](security.md)）
- 生成物のサイズは入力規模に比例する。想定は Chromium 規模で数 GB オーダーであり、これは実測で確定させる
