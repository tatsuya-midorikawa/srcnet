# 改善チケット

2026-09-27 の調査に基づく、機能・使いやすさ・利用資料の改善候補を管理する。
この調査では改善の実装は行わない。起票しただけのチケットは未完了として扱う。

## 調査結果

15 件を起票した。P1 は 8 件、P2 は 6 件、P3 は 1 件で、すべて未着手である。
導入資料、生成物の活用、結果の信頼性、継続利用、CLI / HTML の操作を対象とした。
既存のヘルプ・スキル・HTML 機能は実装済みとして扱い、不足する部分をチケットの範囲にした。

まず P1 の導入・信頼性を整え、037 のメモリ有界化は 039 の参照解決と 040 の増分更新に先行させる。
検索や HTML の独立した操作改善は、各チケットに記載した依存関係を確認して進める。

## 運用

1. 改善項目ごとに 1 ファイルを置き、状態、根拠、対応範囲、受け入れ条件を記録する。
2. 着手時は状態を「対応中」にし、調査時点から実装が変わっていないか確認する。
3. すべての受け入れ条件を満たしたら、チケットに変更内容、検証コマンドと結果、検証環境、完了日を記録する。未検証事項が残る場合は完了にしない。
4. 状態を「完了」にし、同じファイル名のまま [_completed](_completed/) へ移動する。コピーを残さず、この一覧と移動したチケット内の相対リンクも更新する。
5. 対応不要・重複と判断した場合は理由を記録し、実装完了と区別する。

機能変更には [.github/instructions/fsharp-dotnet.instructions.md](../.github/instructions/fsharp-dotnet.instructions.md) の検証基準を適用する。
資料だけの変更でも、掲載コマンドの実行とリンクの確認を行う。

## 調査と検証

- 対象コミット: `2522bb3`。調査開始時の作業ツリーに既存変更はなかった。
- 環境: macOS arm64、.NET SDK 10.0.102、srcnet 0.1.0。
- README、CLI・抽出・保存・安全性・ロードマップの資料、配布用スキル、対応する実装、既存バックログを確認した。
- Release 設定で CLI を起動した。`search --help` と全体ヘルプが同じ 54 行であること、コマンドごとのエラー時 JSON 出力の差を確認した。
- 既存の [テストコーパス](../tests/corpus/) を別出力先へ T1 で索引した。32 ファイル・64 ノード、`complete: true`、終了コード 4 の診断付き生成で、通常の verify は成功した。
- その索引で search / show / neighbors / context と、概要・上限付き・起点付きの HTML 出力を実行した。
- HTML の選択範囲を比較して 041 を再現した。統合ブラウザーと Playwright で 1280 x 800 / 390 x 844 の描画、横方向のはみ出し、選択パネルの操作項目を確認した。
- 全 15 件の必須項目、採番・依存先・一覧との対応、ローカルリンク 93 件、Markdown 診断を検証し、エラーがないことを確認した。アプリの実装への変更はない。

Windows の実行、大規模コーパスの再測定、ソリューション全体のテストは今回実施していない。
n-gram 索引、T2 対応言語の拡大、MCP、impact / explain は [ロードマップ](../docs/roadmap.md) の既存計画として参照し、今回のチケットには混在させない。

## 調査の読み方

各チケットの「確認した事実」は既存資料・実装に基づく。「改善内容」は提案であり、現行機能とは区別する。
不具合の実機再現、静的な実装確認、将来機能の提案を混同しない。
今回の環境は macOS であり、Windows の動作や大規模コーパスの性能を新たに保証するものではない。
