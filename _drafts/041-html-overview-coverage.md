## 確認した事実

- [ExportCommands.fs](../src/Srcnet.Cli/ExportCommands.fs) の `aggregate` は、密インデックス順に Repository / Directory を選び、`maxNodes` に達した後は追加しない。
- コードの説明どおりディレクトリは論理パス順であり、浅い階層を優先する選択ではない。
- [照会スキル](../ai/skills/srcnet/SKILL.md) の Directory coverage 節にも、深い階層が枠を使い切って後続のトップ階層が表示されない制約が記載されている。

2026-09-27、macOS / SDK 10.0.102 / コミット `2522bb3` で次を確認した。

1. [テストコーパス](../tests/corpus/) を T1、並列度 2、単一ファイル上限 1 MiB で別の出力先へ索引した。走査完了は true、32 ファイル・64 ノードで、通常の verify は成功した。
2. 起点を指定しない HTML の候補は Repository / Directory の計 6 ノードだった。
3. `--max-nodes 4` では `corpus`、`cjk`、`micro`、`micro/tests` が選ばれ、トップ階層の `pathological` が省略された。
4. `truncated: true` と省略 2 件は正しく表示された。本件は省略を隠す不具合ではなく、概要としての選択順の改善である。

## 利用者の困りごと

最初の概要でリポジトリの主要な領域を把握したいのに、早いパスの深い階層が表示枠を使い、別の大きな領域が見えなくなる。

## 改善内容

- 幅優先など、Repository と浅い階層を先に含める決定的な選択にする。
- 枠が足りるときはトップ階層を揃え、残りをより深い階層へ割り当てる。
- トップ階層自体が上限を超える場合は、その省略を利用者が判別できるようにする。
- ノード・エッジの上限、集約件数、既知の省略数、未調査の下限表示を維持する。
- 大量のディレクトリを全件 DOM 化したり、概要を無制限にエクスポートしたりしない。

## 対象外

グラフ全体の出力、未実装の中心性による選択、既存のパン・ズーム・フィルターの作り直し。

## 受け入れ条件

- [ ] 上の 4 ノードの例で Repository と 3 つのトップ階層を表示できる。
- [ ] 早いパスに深い・大量の子孫があっても、枠が足りる後続トップ階層が欠落しない。
- [ ] トップ階層だけで上限を超える例、空入力、CJK パスを [ExportTests.fs](../tests/Srcnet.Tests/ExportTests.fs) で検証する。
- [ ] 省略・集約・候補件数が正しく、繰り返し生成した HTML が決定的である。
- [ ] macOS / Windows の対象ブラウザーで表示を確認し、処理時間とメモリを既存の上限内に保つ。
