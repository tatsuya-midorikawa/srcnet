# [P1] 長い索引生成の処理段階と進捗を表示する

- 状態: 未着手
- 種別: 使いやすさ / 長時間処理
- 起票日: 2026-09-27
- 依存: なし。033 と併せて標準出力の契約を保つ。

## 確認した事実

- [Commands.fs](../src/Srcnet.Cli/Commands.fs) の `index` は `buildIndex` の完了を待って `reportIndex` を呼ぶ。
- `buildIndex` は走査・抽出の後に公開処理を行うが、呼び出し側へ途中の進捗を渡す経路がない。
- [Walk.fs](../src/Srcnet.Discovery/Walk.fs) は件数を集計するが、CLI で処理中の進捗として表示するインターフェースはない。
- [Program.fs](../src/Srcnet.Cli/Program.fs) は Ctrl+C をキャンセルへ変換する。キャンセル基盤は既存であり、作り直す必要はない。

## 利用者の困りごと

大きなリポジトリを処理するときに、走査・抽出・保存のどこまで進んだか分からず、停止したのか待つべきなのか判断しにくい。

## 改善内容

- 走査・抽出・整列/保存・公開の現在の段階と、判明している処理件数・バイト数・経過時間を標準エラーへ表示する。
- 全体件数が未確定の段階で、不正確な完了率や残り時間を断定しない。
- 更新頻度を制限し、ファイルごとの同期出力やロックで並列処理を遅くしない。
- TTY とリダイレクト時を区別し、CI ログに制御文字や大量の更新行を流さない。
- 中断要求と後始末の状態を表示し、最後は既存の終了コード・診断へ収束させる。

## 対象外

GUI 進捗画面、常駐サービス、収集テレメトリ、今回の変更だけによるメモリ上限の保証。

## 受け入れ条件

- [ ] 長めの入力で完了前に進捗が見え、保存段階も識別できる。
- [ ] `--json` の標準出力は結果の JSON のみで、進捗が混ざらない。
- [ ] TTY / リダイレクト、成功 / 診断付き / 中断を macOS / Windows で検証する。
- [ ] 進捗の有無で生成物が変わらず、既存のキャンセル・公開・片付け処理を壊さない。
- [ ] 出力頻度・計測用メモリを制限し、同一入力の所要時間と割当量が既定の非劣化基準を満たす。
