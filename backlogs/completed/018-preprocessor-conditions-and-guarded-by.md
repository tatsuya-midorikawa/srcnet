# [P1] プリプロセッサ条件を追跡し GUARDED_BY を生成する

- 種別: 実装 / M2
- 対象: `src/Srcnet.Extraction/`（新規）, `src/Srcnet.Core/Graph.fs:10-27,86-105,282-306`
- 依存: 017
- 参照: [抽出](../../docs/extraction.md) 4.1, [グラフ モデル](../../docs/graph-model.md) 1, 2

## 背景

Linux カーネルでは、シンボルの有無そのものが `CONFIG_*` に依存する。条件を持たないグラフは「この関数はどの構成で存在するのか」に答えられない。

完全なプリプロセス展開は行わない。特定の構成を仮定して枝を捨てると、別構成でのグラフが欠落するためである。

## やること

- `#if` / `#ifdef` / `#ifndef` / `#elif` / `#else` / `#endif` の入れ子を追跡する
- **すべての枝を抽出対象にする**。同名のシンボルが複数の枝に現れる場合は、序数で区別する（017 の規則に従う）
- 条件下にあるシンボルへ `Conditional` フラグと、条件式の原文を属性として付ける
- 条件式に現れる識別子を `ConfigSymbol` ノードにし、シンボルから `GUARDED_BY` エッジを張る。`Kconfig` の定義との突き合わせは M6 で行う
- 関数形式マクロを `Macro` ノードにする。展開はしない。マクロ経由の呼び出しは `AMBIGUOUS` になり得ることを、参照候補の根拠として記録する（016）
- 入れ子の深さと 1 ファイルあたりの条件数に上限を設ける。超過は診断して打ち切り、抽出済みの結果は保持する
- 対応する `#endif` を欠くファイル、`#else` が重複するファイルでも壊れない。壊れた条件構造は診断にして継続する

## 設計上の注意

- 条件式は評価しない。`defined(A) && !defined(B)` は原文のまま保持し、現れる識別子だけを `ConfigSymbol` として取り出す
- 条件式の識別子とマクロ定義は名前空間が同じであるため、`ConfigSymbol` と `Macro` / `Constant` の重複をどう扱うかを決めて記録する
- tree-sitter の `c` 文法は前処理指令をノードとして持つ。行指向の再走査ではなく構文木から取る

## 完了条件

- `#ifdef CONFIG_X` の両方の枝にある定義が、いずれも抽出される
- 抽出したシンボルから `GUARDED_BY` エッジが生成され、`neighbors` で辿れる形で成果物に載る
- 入れ子 1,000 段のファイルで打ち切りと診断が働き、クラッシュしない
- 条件構造が壊れたファイルでも、他のファイルの抽出結果が変わらない
