# [P2] 検出 prefix 末尾の不正 UTF-8 を不完全シーケンスとして許可しない

- 種別: 文字コード判定 / データ品質
- 対象: `src/Srcnet.Text/Encodings.fs:82-93,299-311`
- 信頼度: 100%

## 問題

入力が検出 prefix より長い場合、`isValidUtf8` は末尾から最大 3 バイトを機械的に削り、残りが妥当なら UTF-8 と判定する。削った部分が「妥当な開始バイトから始まるが prefix 終端で不足したシーケンス」かを確認していない。

このため `0xFF` など UTF-8 では常に不正なバイトも、prefix 境界付近にあるだけで無視される。

## 確認結果

65,535 バイトの ASCII、`0xFF`、さらに 1 バイトの ASCII からなる 65,537 バイトのファイルを索引した。

- 検出対象 prefix の末尾は `0xFF`
- `stats` は符号化を `UTF-8` と報告した
- 診断は発生しなかった

## 影響

不正な UTF-8 を正常な UTF-8 として保存し、将来の抽出時に置換、欠落、誤った CJK テキストを生じさせる。入力位置によって判定が変わるため、検出結果の信頼性も失う。

## 対応案

- prefix 全体を状態付き UTF-8 デコーダーで検証する
- 末尾だけが `NeedMoreData` になった場合に限り、不完全シーケンスとして許可する
- 不正な lead byte、overlong、surrogate、範囲外 scalar は prefix 末尾でも拒否する

## 完了条件

- 妥当な 2〜4 バイトシーケンスの途中で prefix が終わるケースを許可する
- `0x80`、`0xC0`、`0xC1`、`0xF5`〜`0xFF` を末尾へ置いたケースを拒否する
- prefix 境界の前後をずらした property test で判定が一貫する
