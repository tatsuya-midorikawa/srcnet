# [P0] 抽出パイプラインの土台と決定的な実行順序を用意する

- 種別: 実装 / M2
- 対象: `src/Srcnet.Extraction/`（新規）, `src/Srcnet.Discovery/Walk.fs:56-74`, `src/Srcnet.Discovery/Content.fs:52-193`, `src/Srcnet.Cli/Commands.fs:144-197`
- 依存: なし
- 参照: [抽出](../docs/extraction.md) 2, [ロードマップ](../docs/roadmap.md) M2, [テスト](../docs/testing.md) T-1

## 背景

M2 は T1（行指向）と T2（構文）の抽出結果をグラフへ載せる。現在は構文解析層（`Parsing` / `SyntaxTree` / `Grammars`）まで用意されているが、その上に「木からグラフを作る」層がない。

抽出結果を運ぶ型と、走査から書き出しまでを繋ぐ経路を先に決めないと、T1 と T2 の実装が互いに別の中間表現を持つことになる。

## 現状

- `Content.ContentReader.Read` はファイルを 1 回読み、内容ハッシュ・符号化・行数だけを返して本文を捨てる
- `Walk.DiscoveredFile` は本文を持たない
- `Writer.IndexInput` はディレクトリとファイルだけを受け取る（`src/Srcnet.Storage/Writer.fs:37-52`）
- したがって、抽出を後段に置くとファイルを二度開くことになり、走査時間がほぼ倍になる

## やること

- `Srcnet.Extraction` に言語非依存の抽出結果モデルを定義する
  - `ExtractedSymbol`: 種別、短い名前、修飾名、親スコープ、行範囲、バイト範囲、`NodeFlags`、`docRef` の範囲
  - `ExtractedReference`: 参照候補（記録形式は 016 で定める）
  - `ExtractedFile`: 1 ファイル分の結果と、その抽出に使った段階（T0 / T1 / T2）
- 抽出は走査の 1 回読みの中で行い、ファイルを二度開かない。読み取り済みバイト列をワーカー単位のバッファで抽出器へ渡す
- 抽出対象にする上限を `MaxFileSizeBytes` とは別に設ける。ハッシュは取れるが抽出はしない、という状態を表現できるようにする
- 1 ファイルあたりのシンボル数と参照数に上限を設け、超過は診断して切り捨てる。切り捨てたファイルには印を残す
- 決定的な順序を保証する
  - ファイル間: 論理パスの序数昇順（既存の `WalkResult` の順序）
  - ファイル内: バイト位置の昇順、同位置は種別コードの昇順
  - ワーカーはファイル単位で結果を返し、結合は序数順に行う。完了順に追記しない
- 抽出の失敗（解析器不在、時間切れ、取り消し、構文誤り）は診断にして走査全体を止めない

## 設計上の注意

- 本文を保持するのは抽出中だけにする。`ExtractedFile` に原文を残すと、常駐メモリが入力規模に比例する
- 抽出器は対象リポジトリのバイト列しか見ない。パス以外の環境情報（現在時刻、環境変数、実行順）を結果へ混ぜない

## 完了条件

- `--jobs 1` と `--jobs 16` の抽出結果が完全に一致する（T-1）
- 読み取れないファイル、上限超過のファイルが混ざっても走査が完了し、診断で理由を説明できる
- 抽出対象の言語を含まないコーパスで、走査時間に計測可能な回帰がない
- 抽出中の取り消しが定めた時間内に効き、公開済みの成果物を変更しない
